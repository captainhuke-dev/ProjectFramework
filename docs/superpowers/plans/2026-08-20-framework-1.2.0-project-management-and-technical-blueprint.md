# Framework 1.2.0 Project Management & Technical Blueprint Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Release Project Source Framework `1.2.0` / Schema `1.0.0` with Project-management control, technical blueprint/install documentation, Source/Docker dual-mode semantics, and a synthetic Golden Reference — without adding executable software, Docker runtime artifacts, CI, or automation.

**Architecture:** Preserve mandatory core namespace `00–17`; standardize `40 Technical Design`, `60 Deployment Plan`, and `91 Project Management Control` as conditional extended documents. Integrate their semantics into current routing, health, decisions, handoff, actors, manifest, migration, and pressure scenarios. The Framework describes how software Projects should document Tech Stack, source responsibilities, installation, Source/Docker deployment, verification, and operations; it does not implement that software.

**Tech Stack:** Markdown and YAML governance/documentation artifacts plus Git/GitHub version control. No application runtime, executable validator, third-party library, Docker artifact, installer, CI workflow, scheduler, or enforcement service is introduced.

**Spec:** `docs/superpowers/specs/2026-08-20-framework-1.2.0-project-management-and-technical-blueprint-design.md`

## Global Constraints

- Framework version becomes exactly `1.2.0`; Project Source Schema remains exactly `1.0.0`.
- `00–05` and `09–17` retain existing mandatory semantics.
- `06 Architecture`, `07 Implementation Plan`, `08 Open Issues`, `40 Technical Design`, `60 Deployment Plan`, and `91 Project Management Control` are `CONDITIONAL`.
- `18–19` remain `RESERVED` and receive no starter files.
- `90` remains the general/special governance-extension anchor; `91` becomes standard conditional Project Management Control in `1.2.0+`; `92–99` remain extension space unless a later Framework revision governs them.
- Canonical `91` object homes are exactly `RISK-*`, `ASM-*`, `MS-*`, `OUT-*`, `DEP-*`, `CR-*`, `GATE-*`.
- `ISS-*`, `DRIFT-*`, `CONFLICT-*`, including `issue_type: KNOWLEDGE_DEBT`, remain canonical in `08 Open Issues`.
- `DEC-*` remains canonical in `04 Decision Log`; Decision Revalidation is an extension of the Decision record, not a new registry.
- Responsibility Mapping remains in `11 Actor Registry`; `Responsibility ≠ Authority`; authorization remains `AUTH-*` / `DEL-*` in `12 Authorization Registry`.
- Project Health remains a multi-dimensional derived current assessment in `03 Current State`; no automatic weighted score is added.
- Review Cadence supports exactly the conceptual modes `TIME_BASED` and `EVENT_BASED`; no scheduler/reminder runtime is created.
- Deployment support states are `SOURCE_ONLY`, `DOCKER_ONLY`, `SOURCE_AND_DOCKER`, `NOT_APPLICABLE`.
- `SOURCE_AND_DOCKER` requires one declared application/configuration/data/security/persistence contract; intentional differences use Deployment Mode Variance; unexpected mismatch is `DRIFT-*`.
- Framework technical scope is documentation/blueprint only. Do not add application source code, Dockerfile, Compose/Kubernetes/Helm artifacts, install scripts, package-manager tooling, validator/CLI, GitHub Actions/CI, deployment automation, dashboard, scheduler, or runtime enforcement.
- A real Project's `60 Deployment Plan` may contain concrete commands/paths only when they are verified Project truth. The Framework distribution and synthetic Golden Reference must not invent executable commands for nonexistent software.
- New Project bootstrap remains from canonical repository `main`; immutable tags/SHA and branch protection remain optional assurance.
- Existing Projects remain locally pinned and never auto-upgrade; migration to `1.2.0` uses `MIG-*` plus explicit approval.
- A Brownfield custom document already occupying slot `91` must never be overwritten. Assess through `MIG-*`, preserve identity/history/references, relocate only with approval, then activate standard `91`.
- Existing free-text notes must never be automatically converted into `RISK-*`, `ASM-*`, `MS-*`, `OUT-*`, `DEP-*`, `CR-*`, or `GATE-*`; promotion requires enough current semantics, ownership, status, and epistemic/evidence state to avoid fabrication.
- Current Stable IDs remain materialized current projections; archive traversal must not be required to determine current truth.
- Historical Framework amendments remain immutable; add a new amendment rather than editing old amendment files.
- ChatGPT and Claude shared governance blocks remain byte-identical.
- Actual secret values remain forbidden; `SECRET-*` stores external-reference metadata only.
- `independent_fresh_agent_green_run` remains `false` unless genuine external clean-context evidence exists.
- Golden Reference is illustrative, not normative. Core Governance and active Framework win on conflict.
- Golden Reference contains documentation only; no source code, Dockerfile/Compose, scripts, package manifests, CI, binary artifacts, or real secrets.
- If local Git checkout is unavailable, use equivalent fresh GitHub reads/compares before and after every task. A successful write response alone is not verification.
