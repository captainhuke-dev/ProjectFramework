# Framework 1.2.0 Project Management & Technical Blueprint Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Release Project Source Framework `1.2.0` / Schema `1.0.0` with stronger Project-management governance, technical blueprint/install documentation, Source/Docker dual-mode semantics, and a synthetic Golden Reference — without adding executable implementation code or automation.

**Architecture:** Keep the mandatory core namespace `00–17` unchanged. Add `40 Technical Design`, `60 Deployment Plan`, and `91 Project Management Control` as conditional extended documents; integrate their semantics into existing routing, health, decision, handoff, actor, manifest, and pressure-scenario surfaces. The release remains documentation/governance only: ProjectFramework may precisely define or document software responsibilities and installation behavior, but it does not create application code, Docker artifacts, installers, validators, CI, or runtime automation.

**Tech Stack:** Markdown and YAML governance/documentation artifacts; Git/GitHub for version control and review. No application runtime, package dependency, executable validator, CI workflow, Docker runtime artifact, or third-party library is introduced by this plan.

**Spec:** `docs/superpowers/specs/2026-08-20-framework-1.2.0-project-management-and-technical-blueprint-design.md`

## Global Constraints

- Target Project Source Framework version: `1.2.0`.
- Project Source Schema remains exactly `1.0.0`.
- `00–05` and `09–17` retain existing mandatory semantics.
- `06 Architecture`, `07 Implementation Plan`, and `08 Open Issues` remain `CONDITIONAL`.
- `18–19` remain `RESERVED` and receive no starter files.
- `40 Technical Design`, `60 Deployment Plan`, and `91 Project Management Control` are `CONDITIONAL`; they are never auto-created merely to make a Project tree look complete.
- `90` remains the general/special governance-extension anchor; `91` becomes the standard conditional Project Management Control slot in Framework `1.2.0+`; `92–99` remain Project-specific/Governance Extension space unless governed otherwise by a future Framework revision.
- Canonical `91` object homes are exactly: `RISK-*`, `ASM-*`, `MS-*`, `OUT-*`, `DEP-*`, `CR-*`, `GATE-*`.
- `ISS-*`, `DRIFT-*`, `CONFLICT-*`, and `KNOWLEDGE_DEBT` remain in `08 Open Issues`; Knowledge Debt does not get a new registry.
- `DEC-*` remains canonical in `04 Decision Log`; Framework `1.2.0` adds revalidation semantics without relocating Decisions.
- Responsibility mapping remains in `11 Actor Registry`; `Responsibility ≠ Authority`; actual authorization remains in `12 Authorization Registry` through `AUTH-*` / `DEL-*`.
- Project Health remains a derived current assessment in `03 Current State`; no opaque aggregate score is introduced.
- Deployment support states are exactly `SOURCE_ONLY`, `DOCKER_ONLY`, `SOURCE_AND_DOCKER`, and `NOT_APPLICABLE`.
- `SOURCE_AND_DOCKER` requires one application/configuration/data/security contract plus explicit Deployment Mode Variance for intentional differences; unexpected mismatch is `DRIFT-*`.
- Framework technical scope is documentation/blueprint only. Do not add application source code, Dockerfile, Compose/Kubernetes/Helm manifests, install scripts, package-manager tooling, validator/CLI, GitHub Actions/CI, migration engine, scheduler, background automation, dashboard, or runtime enforcement.
- A real Project's `60 Deployment Plan` may contain concrete verified commands/paths when they are real Project truth; the Framework distribution and Golden Reference must not invent executable commands for nonexistent software.
- New Project bootstrap remains from canonical repository `main`; exact Git tag/SHA and branch protection remain optional assurance, not operational prerequisites.
- Existing Projects remain locally pinned and never auto-upgrade; Framework `1.2.0` adoption is through `MIG-*` plus explicit approval.
- Brownfield slot `91` collision must never be overwritten; use `MIG-*` and approved relocation to a suitable free `92–99` or other semantically correct slot before standard `91` activation.
- Current Stable IDs remain materialized current projections; archive traversal must not be required to determine current semantics.
- Historical Framework amendments are immutable. Add a new amendment; do not edit previous amendment files.
- ChatGPT and Claude shared governance contract blocks remain byte-identical.
- Actual secret values remain forbidden. `SECRET-*` stores references/metadata only.
- `independent_fresh_agent_green_run` must not be changed to `true` without real external clean-context evidence.
- Golden Reference is illustrative, never normative; Core Governance wins on conflict.
- Golden Reference contains documentation only and no actual application/Docker/CI implementation artifacts.
- If execution cannot use a local checkout, perform equivalent fresh GitHub file/directory/compare reads before and after each task. Do not treat a successful write response as verification.
