# Framework 1.2.6 Bootstrap Location Semantics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Release Project Source Framework `1.2.6` / Schema `1.0.0` with deterministic Bootstrap Location Semantics for Framework Source, Remote Location, MCP Location, Local Workspace, File Storage Location, and dynamic current branch/worktree state without creating a second initialized-Project authority.

**Architecture:** Keep active local `FRAMEWORK-001` as the canonical initialized-Project routing authority. Add a bootstrap/discovery layer that supplies deterministic pre-`FRAMEWORK-001` starting locations, map Google Drive bootstrap storage to the existing dedicated `google_drive` binding, add provider-neutral governed storage entries only for S3/NAS/filesystem/other scopes, and preserve Git branch/integration/implementation/runtime authority as separate contracts. Project-specific Bootstrap Location values live in the Project instruction/configuration layer outside the shared launcher contract; launchers define only semantics and precedence.

**Tech Stack:** Markdown, YAML, Git/GitHub, Windows/local MCP execution, Python standard library for non-persistent structural verification. No application runtime, validator product, hook, bot, CI/CD, automatic repository/storage selector, background agent, filesystem watcher, secret store, branch switcher, or connector credential mechanism is introduced.

**Spec:** `docs/superpowers/specs/2026-08-22-framework-1.2.6-bootstrap-location-semantics-design.md`

## Global Constraints

- Target Project Source Framework is exactly `1.2.6`; Project Source Schema remains exactly `1.0.0`.
- Existing initialized Projects remain locally pinned and do not auto-upgrade.
- Add no semantic slot, Stable-ID namespace, Project lifecycle state, Git freshness state, branch-authority field, or new authority family.
- Preserve Framework `1.2.1` Externalized Working Memory / Chat Lifecycle semantics.
- Preserve Framework `1.2.2` Canonical Integration Target, Base Freshness, `STACKED_WORK`, Pre-Merge Base Freshness Gate, and `Mergeable ≠ Acceptable`.
- Preserve Framework `1.2.3` Canonical Implementation Source / Development Workspace / Runtime Authority semantics.
- Preserve Framework `1.2.4` Project Location Binding, `BOUND | NOT_APPLICABLE | VERIFICATION_REQUIRED`, fail-closed routing, and one-off exact-target semantics.
- Preserve Framework `1.2.5` Environment-Scoped Local Workspace Binding, verified Material Task completion checkpoints, progressive/risk-scoped verification, evidence reuse, and Response Close Completeness Gate.
- Bootstrap Location Block is discovery/routing input before active governance is resolved; active `FRAMEWORK-001` is authoritative for initialized-Project Project Location state.
- Bootstrap/Root Governance mismatch is fail-closed for the affected Material mutation; neither side is silently rewritten.
- `Framework Source ≠ Remote Location ≠ MCP Location ≠ Local Workspace ≠ File Storage Location ≠ current branch/worktree ≠ Project Location Binding authority ≠ Canonical Integration Target ≠ Canonical Implementation Source ≠ Runtime Location`.
- `current branch/worktree` is dynamic observed Git state and is verified each session / whenever Material Git execution state matters; do not persist a static branch/worktree as bootstrap authority.
- MCP `workspaceId`, editor handles, active/recent workspace lists, search ranking, drive letters, and local mounts are routing evidence only where a more durable identity exists.
- File Storage Location reuses exactly `BOUND | NOT_APPLICABLE | VERIFICATION_REQUIRED`; do not create provider-specific uncertainty states.
- File Storage verification status reuses exactly `VERIFIED | USER_CONFIRMED | VERIFICATION_REQUIRED`.
- `BOUND` File Storage requires sufficient durable provider identity; `BOUND` pairs only with `VERIFIED` or `USER_CONFIRMED`, never `verification_status: VERIFICATION_REQUIRED`.
- Known-applicable but unresolved storage scope is `VERIFICATION_REQUIRED` and fail-closed for Material mutation.
- A Project with no external/non-repository storage may omit storage entries entirely; do not create synthetic provider `NOT_APPLICABLE` entries.
- Absence of a storage entry never authorizes fallback to a recent/search-ranked bucket, folder, share, or mount.
- Existing dedicated `google_drive` Project Location Binding remains the sole active Root Governance authority for Google Drive Project-root routing. Do not create a duplicate generic Google Drive authority entry.
- Generic governed `file_storage_locations` in active `FRAMEWORK-001` are for S3/NAS/filesystem/other external storage scopes. A Project-level bootstrap Google Drive entry maps to the existing dedicated `google_drive` binding.
- File Storage Location does not automatically become Canonical Implementation Source, Runtime Persistent-State Boundary, or backup policy.
- Project-specific Bootstrap Location values are supplied/configured outside the shared ChatGPT/Claude launcher contract. Shared launchers contain semantics only and never hard-code another Project's repository/path/storage values.
- ChatGPT/Claude shared launcher marker bodies remain byte-identical and each complete launcher remains `<= 4,500` Unicode characters. Current baseline is 4,311 ChatGPT characters and 4,302 Claude characters, so wording must be compressed rather than blindly appended.
- Historical amendments/specs remain historical. Create one new timestamped Framework `1.2.6` amendment rather than rewriting prior amendments.
- The approved design pressure scenarios `87–106` already exist on the planning branch and must remain contiguous, unique, before `GREEN Run Instructions`, and semantically satisfied by the implementation.
- No executable enforcement tooling is authorized by this plan.
