# Framework 1.2.6 Bootstrap Location and File Storage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Release Project Source Framework `1.2.6` / Schema `1.0.0` with deterministic bootstrap-location semantics for Framework Source, Remote Location, File Storage Location, MCP Location, Local Workspace, and dynamically observed current branch/worktree, plus a generalized governed File Storage Binding for non-Google-Drive external storage such as S3/object storage, NAS/file shares, and multiple content-scoped storage owners while the dedicated Google Drive binding remains canonical for Drive without weakening existing Project Location, Git, implementation, runtime, authority, persistence, or verification rules.

**Architecture:** Keep active local `FRAMEWORK-001` as the single Project governance authority after it resolves. Add a compact Project Location bootstrap preamble outside the Project Source semantic-slot namespace so an Agent can deterministically locate Framework upstream, remote discovery, file storage, MCP routing, and local workspace before authority is known. Add generalized non-Drive `File Storage Binding` under `FRAMEWORK-001` Project Location Binding, preserve the dedicated provider-specific Google Drive binding as the canonical Framework `1.2.6` Drive authority, and keep File Storage distinct from repository routing, Local Workspace, Canonical Implementation Source, Runtime/Persistent-State authority, and mutation authorization. Current branch/worktree remains volatile observed Git state and never becomes bootstrap authority.

**Tech Stack:** Markdown, YAML, Git/GitHub, Windows/local MCP execution, Python standard library for structural verification. No application runtime, storage synchronization, validator/CLI, hook, bot, scheduler, GitHub Actions/CI, filesystem watcher, automatic workspace selector, or enforcement service is in scope.

**Spec:** `docs/superpowers/specs/2026-08-22-framework-1.2.6-bootstrap-location-semantics-design.md` — `USER_APPROVED_REVISION_2` + `WRITTEN_SPEC_APPROVED` after storage-state review/fix.

## Global Constraints

- Target Project Source Framework is exactly `1.2.6`; Project Source Schema remains exactly `1.0.0`.
- Preserve Framework `1.2.1–1.2.5` semantics unless Revision 2 explicitly refines them.
- Existing initialized Projects remain governed by their local pinned active `FRAMEWORK-001`; no auto-upgrade from upstream.
- Preserve exactly six bootstrap/execution concepts: `Framework Source`, `Remote Location`, `File Storage Location`, `MCP Location`, `Local Workspace`, and dynamic `current branch/worktree`.
- If a declared Local Workspace contains a valid active `FRAMEWORK-001`, read/adopt that Root Governance first; Remote Location must never compete with or replace it because remote content looks newer.
- Bootstrap locators help find/rout work but never silently become Project authority.
- `Remote Location ≠ Repository Location Binding`.
- `File Storage Location ≠ File Storage Binding`.
- `MCP Location ≠ Local Workspace Binding`.
- `Local Workspace ≠ Local Workspace Binding`.
- `Repository Location Binding ≠ File Storage Binding ≠ Local Workspace Binding ≠ current branch/worktree ≠ Canonical Integration Target ≠ Canonical Implementation Source ≠ Runtime Location`.
- Project Location Binding must not introduce `canonical_branch` or another competing Git integration authority.
- Current branch/worktree is always fresh-observed when material; Project/bootstrap instructions may persist only `DYNAMIC` / `VERIFY_EACH_SESSION` intent, not a concrete branch as authority.
- File Storage Binding reuses exactly `BOUND | NOT_APPLICABLE | VERIFICATION_REQUIRED`; no storage-specific state family is introduced.
- File Storage verification reuses exactly `VERIFIED | USER_CONFIRMED | VERIFICATION_REQUIRED`; `BOUND` pairs only with `VERIFIED` or `USER_CONFIRMED`, never `verification_status: VERIFICATION_REQUIRED`.
- Generic governed File Storage may support `S3`, S3-compatible/object storage, `NAS`, `SMB`, `NFS`, `SHAREPOINT`, `FILE_SERVER`, `FILESYSTEM`, and `OTHER` provider types without making provider vocabulary a lifecycle state.
- A Project with no external/non-repository storage may omit generic File Storage entries; do not create synthetic provider `NOT_APPLICABLE` entries merely to fill a template.
- Known-applicable but unresolved storage is `VERIFICATION_REQUIRED`; absent/unresolved storage never authorizes fallback to recent/search-ranked targets.
- Multiple storage bindings are valid when content scopes are distinct; one governed content scope has one declared authoritative owner at a time.
- `project_location_binding.google_drive` remains the canonical Framework `1.2.6` Root Governance representation for Google Drive. A bootstrap Google Drive locator maps to it; generic File Storage MUST NOT duplicate Drive authority for the same target/content scope.
- Normalizing Google Drive into generic File Storage is outside Framework `1.2.6`; if a future Framework authorizes it, the change requires a governed `MIG-*` migration with history preservation.
- File Storage Binding is Project file/object routing/content ownership. It is not automatically Canonical Implementation Source, Runtime persistent-state authority, Data/Storage Authority, backup authority, or deployment authority.
- Mounted/synced/cached storage paths are routing/mapping evidence only unless another governed contract explicitly assigns them a different role.
- Actual storage credentials are prohibited in Project Location metadata; use `SECRET-*` external-reference metadata only.
- Location correctness never grants mutation authority. `AUTH-*`, `DEL-*`, R0–R3, User approval/standing authorization, scope, REQ/DEC, and other gates remain independently binding.
- A one-off User Explicit Instruction naming an exact repository/workspace/storage target may authorize only that otherwise-permitted action; it does not persistently rewrite bootstrap or Root Governance locations.
- Persistent bootstrap/governed location changes require explicit approval and coordinated update of each affected layer; neither layer silently supersedes the other.
- Platform launcher shared-contract bodies remain byte-identical and each complete launcher remains `<= 4,500` Unicode characters.
- No semantic slot, Stable-ID family, Project lifecycle state, Git freshness state, or Epistemic Status is added.
- Historical amendments/specs remain historical and are not rewritten to adopt 1.2.6 wording.
- Each Material implementation Task follows Framework `1.2.5`: affected/risk-scoped verification PASS + observed completion commit before durable `DONE`; `commit ≠ push`.
- Task-level checks are proportional; Logical Checkpoint is continuity integrity; final unchanged candidate receives one `RELEASE_FULL`; integration revalidates Base Freshness/evidence validity.
