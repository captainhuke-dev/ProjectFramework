# ProjectFramework 1.2.0 — Project Management & Technical Blueprint Design

**Status:** APPROVED DESIGN SECTIONS — pending final written-spec review

**Repository:** `captainhuke-dev/ProjectFramework`

**Design branch:** `framework-1.2.0-design`

**Base release:** Project Source Framework `1.1.5` / Project Source Schema `1.0.0`

**Target release:** Project Source Framework `1.2.0` / Project Source Schema `1.0.0`

**Approval basis:** User explicitly approved Section 1 (Project Management Architecture), Section 2 (Technical Blueprint), and Section 3 (Project Operating & Review Model) on 2026-08-20.

---

## 1. Purpose

Framework `1.2.0` expands ProjectFramework in two directions while preserving the concept-first boundary established in `1.1.5`:

1. improve real Project management through explicit Risk, Assumption, Milestone, Outcome, Dependency, Change Request, Review Gate, Project Health, Responsibility, Decision Revalidation, and Knowledge-Debt semantics;
2. improve governance of Projects that contain software/code by defining a Technical Blueprint for Tech Stack, source structure, configuration, installation, Source deployment, Docker deployment, operational verification, upgrade, rollback, and backup/restore.

This release remains a **conceptual Project governance and planning framework**. It defines what Project Source should capture, how concepts relate, where current truth lives, and what a Human/Agent must be able to determine. It does not implement application code, installers, validators, CLIs, Docker artifacts, CI workflows, deployment automation, or runtime enforcement.

---

## 2. Design Boundary

### 2.1 Concept-first rule

ProjectFramework may define:

- governance concepts and canonical object homes;
- document structures and semantic roles;
- architecture and deployment blueprints;
- Tech Stack declarations;
- installation requirements and project-specific installation documentation structure;
- Source/Docker responsibility and parity contracts;
- review, readiness, health, risk, and management semantics;
- examples and synthetic reference projects.

ProjectFramework MUST NOT, from this release alone, create or require executable implementation artifacts such as:

```text
application source code
Dockerfile
docker-compose.yml / compose.yaml
Kubernetes / Helm manifests
shell / PowerShell installers
Python / Node / Go tooling
validator / CLI
GitHub Actions / CI pipeline
migration engine
background automation
runtime enforcement service
```

A real Project may already contain such implementation artifacts. Project Source may document, reference, govern, and verify them. Creating or modifying those implementation artifacts is a separate explicit implementation scope.

### 2.2 Technical documentation may be concrete

The concept-first boundary does **not** require installation documentation to stay vague. When a real Project already has verified installation/runtime behavior, its `60 Deployment Plan` may contain concrete project-specific commands, paths, package names, ports, environment keys, or operational procedures needed to install and operate that Project.

The boundary is:

> ProjectFramework defines and governs the installation contract; it does not itself author the software implementation merely because the contract describes how the software is installed.

---

## 3. Versioning and Compatibility

Target Framework version:

```text
1.1.5 → 1.2.0
```

Project Source Schema remains:

```text
1.0.0
```

Rationale:

- core front-matter mechanics do not change;
- semantic slots already support the extended `00–99` taxonomy;
- the release adds standard governance concepts and conditional extended documents rather than changing the serialization/schema model;
- existing Projects remain pinned and never auto-upgrade.

An existing Project upgrades only through a governed `MIG-*` assessment and explicit approval.

# Part I — Project Management Architecture

## 4. Standard Conditional Extended Document: `91 Project Management Control`

Framework `1.2.0` standardizes:

```text
91 Project Management Control    CONDITIONAL
```

`91` is the canonical home for cross-cutting Project-management control objects that do not belong in the core `00–17` registries:

```text
RISK-*   Risk
ASM-*    Assumption
MS-*     Milestone
OUT-*    Outcome
DEP-*    Dependency
CR-*     Change Request
GATE-*   Review / Phase Gate
```

### 4.1 Applicability

Create active `91 Project Management Control` when at least one governed object above is materially applicable to the Project.

Do not create an empty `91` solely to make the Project tree look complete.

### 4.2 Core and extended namespace

Framework `1.2.0` preserves:

```text
00–05    existing mandatory core semantics
06–08    CONDITIONAL
09–17    existing mandatory core semantics
18–19    RESERVED
```

For the governance-extension range:

```text
90       General / Special Governance Extension anchor
91       Project Management Control — STANDARD CONDITIONAL in Framework 1.2.0+
92–99    Project-specific / Governance Extension unless governed otherwise by a future Framework revision
```

`91` is a standard **extended** semantic document; it does not become part of the mandatory `00–17` bootstrap set for every Project.

### 4.3 Integration with core documents

`91` owns the full current management records. Other documents summarize or reference them:

```text
01 Index
  → routes to 91 when active

03 Current State
  → summarizes health and active management signals

04 Decision Log
  → references relevant RISK / ASM / CR / GATE and revalidation triggers

07 Implementation Plan
  → references MS / DEP / GATE / CR / RISK when implementation work exists

08 Open Issues
  → owns materialized issues, DRIFT, CONFLICT, and KNOWLEDGE_DEBT issues

09 Handoff
  → references continuation-relevant active RISK / ASM / DEP / MS / CR / GATE

11 Actor Registry
  → records responsibility mapping without granting authority

14 Manifest
  → includes active 91 when present
```

No object is duplicated as authoritative current truth in multiple documents.

## 5. `RISK-*` — Risk Management

A Risk is a material uncertain future event or condition that may affect Project objectives.

A Risk is **not** an Issue. `ISS-*` represents a problem/condition that has already materialized or currently exists.

Minimum Risk record:

```text
RISK-ID
Title
Risk Statement
Category
Probability
Impact
Exposure / Severity when used
Trigger / Early Warning
Mitigation
Contingency
Owner
Review Trigger / Review By
Status
Related REQ / DEC / ASM / DEP / MS / OUT / CR / EVD
Materialized Issue when applicable
```

Recommended statuses:

```text
IDENTIFIED
OPEN
MITIGATING
MONITORING
ACCEPTED
MATERIALIZED
CLOSED
SUPERSEDED
```

Typical lifecycle:

```text
IDENTIFIED → OPEN → MITIGATING / MONITORING → CLOSED
                  ├──→ ACCEPTED → MONITORING / CLOSED
                  └──→ MATERIALIZED → ISS-*
```

`MATERIALIZED` preserves the Risk record and links the resulting `ISS-*`; the Risk is not deleted or silently rewritten into an Issue.

`ACCEPTED` means the remaining exposure is intentionally accepted. Material Risk acceptance must identify the applicable decision/authority and review trigger where continued monitoring is needed.

## 6. `ASM-*` — Assumption Management

An Assumption is a proposition currently relied upon without sufficient verification to treat it as established truth.

Minimum Assumption record:

```text
ASM-ID
Statement
Basis
Why It Matters
Impact If False
Verification Method
Verification Owner
Review Trigger / Review By
Status
Evidence
Related REQ / DEC / RISK / DEP / MS / CR
```

Lifecycle:

```text
UNVERIFIED
   ├──→ VALIDATED
   ├──→ INVALIDATED
   └──→ SUPERSEDED
```

Invalidation must trigger impact assessment. Depending on affected truth it may lead to `DRIFT-*`, `CR-*`, re-planning, Decision revalidation, Requirement revision, or Risk/Issue updates.

A validated assumption may become verified Project truth only when the appropriate authoritative source/evidence supports that promotion.

## 7. `ACT-*` vs `MS-*` vs `OUT-*`

Framework `1.2.0` makes the distinction explicit:

```text
ACT-*  = work/action that must be performed
MS-*   = significant checkpoint/state that must be reached
OUT-*  = result/benefit/effect the Project intends to achieve
```

Completion does not automatically propagate upward:

```text

  ≠ MS REACHED
  ≠ OUT ACHIEVED
```

## 9. `CR-*` — Scope and Change Control

`CR-*` governs a proposed material change before the change becomes current Project truth.

`CHG-*` in `10 Change Log` remains historical truth about changes that actually occurred.

Therefore:

```text
CR-*  = proposed change + impact assessment + decision path
CHG-* = historical record of applied/observed change
```

Minimum Change Request record:

```text
CR-ID
Requested Change
Reason / Trigger
Requester
Affected Scope
Impact Assessment
Affected REQ / DEC / Architecture / Technical Design / Deployment / MS / OUT / RISK / DEP
Authority / Approval Requirement
Decision
Implementation / Migration References when applicable
Verification Requirement
Status
```

Impact Assessment must consider, when applicable:

```text
Scope
Requirements
Decisions
Architecture
Tech Stack
Source Structure
Configuration
Installation / Deployment Modes
Data / Migration
Security / Authority
Milestones / Outcomes
Risk
Dependencies
Schedule / Effort
Operations / Handoff
```

Lifecycle:

```text
PROPOSED
  ↓
IMPACT_ASSESSED
  ├──→ APPROVED → IMPLEMENTING → IMPLEMENTED → CLOSED
  ├──→ REJECTED
  └──→ CANCELLED
```

Approval of a `CR-*` authorizes only the governed change described by its scope and authority model; it does not silently grant unrelated implementation authority.

## 10. `GATE-*` — Review / Phase Gate

`GATE-*` represents a governed checkpoint where a defined scope is reviewed against explicit entry/exit criteria.

Common gate purposes may include:

```text
DISCOVERY_READY
DESIGN_READY
IMPLEMENTATION_READY
DEPLOYMENT_READY
RELEASE_READY
HANDOFF_READY
PROJECT_CLOSE_READY
CUSTOM
```

Not every Project needs every Gate.

Minimum record:

```text
GATE-ID
Purpose
Affected Scope
Entry Criteria
Exit / Pass Criteria
Required Evidence
Related REQ / DEC / RISK / ASM / DEP / MS / CR
Review Owner
Required Authority
Status
Findings
Exceptions / Waiver
Next Action
Reviewed At
```

Lifecycle:

```text
PLANNED
  ↓
READY_FOR_REVIEW
  ├──→ PASSED
  ├──→ FAILED
  └──→ WAIVED
```

`WAIVED` requires an explicit rationale plus the applicable authority/decision reference. A Gate blocks only its governed scope unless the Project-specific rule explicitly defines broader impact.

# Part II — Project Operating & Review Model

## 11. Multi-Dimensional Project Health in `03 Current State`

Project Health is a current assessment and therefore belongs in `03 Current State`, not a new registry.

Standard dimensions:

```text
Scope
Progress / Schedule
Risk
Quality / Validation
Dependencies
Authority
Knowledge
Readiness
Technical / Deployment    when applicable
```

Each applicable dimension uses:

```text
GREEN
AMBER
RED
UNKNOWN
```

A non-applicable optional dimension is omitted rather than reported as `GREEN`.

Each health dimension must record or resolve:

```text
State
Reason
Supporting Stable IDs / Evidence
Owner
Last Reviewed
Next Review / Trigger when applicable
```

### 11.1 No opaque aggregate score

Framework does not define an automatic weighted health score. Multiple dimensions remain visible so a critical `RED` cannot be averaged away by unrelated `GREEN` dimensions.

A Project-specific overall label may exist only if its derivation and limitations are explicit; it must not replace the dimensional view.

### 11.2 Health is derived assessment, not source replacement

Health entries summarize evidence/current objects. They do not replace canonical Risk, Issue, Dependency, Requirement, Authority, or Gate records.

## 13. Responsibility Mapping in `11 Actor Registry`

`11 Actor Registry` may contain responsibility mappings using:

```text
Responsible
Accountable
Consulted
Informed
```

Each mapping is keyed by a governed scope reference such as a Stable ID, semantic document, defined workstream, or explicitly named Project scope. Responsibility rows are versioned through the active `11` revision/history; they do not require a new Stable-ID object type in Framework `1.2.0`.

Example semantic relationship:

```text
Scope: MS-004 Production Launch
Responsible: ACTOR-003
Accountable: ACTOR-001
Consulted: ACTOR-005
Informed: ACTOR-006
```

### 13.1 Responsibility is not Authority

Framework preserves the existing invariant:

```text
Responsibility ≠ Authority
```

Being Responsible or Accountable for a task/milestone does not itself grant permission for an R2/R3 mutation, approval, deployment, production access, or external action.

Actual authorization remains canonical in `12 Authorization Registry` through `AUTH-*` / `DEL-*` and the risk/approval rules.

# Part III — Technical Blueprint for Projects with Code

## 16. Applicability and Document Boundaries

Framework `1.2.0` uses existing extended taxonomy anchors:

```text
40 Technical Design      CONDITIONAL
60 Deployment Plan       CONDITIONAL
```

### 16.1 `06 Architecture` vs `40 Technical Design`

`06 Architecture` remains the conditional core architecture view: major systems/components/interfaces, boundaries, data flow, constraints, and key architecture Decisions.

`40 Technical Design` is the deeper implementation-facing **blueprint** used when a Project has meaningful software/technical implementation details such as Tech Stack, source topology, runtime, configuration, detailed interfaces, or deployment-mode architecture.

For a small Project, `06` may be sufficient. Do not duplicate the same authoritative payload in both. `40` should deepen or reference `06`, not fork it.

### 16.2 `07 Implementation Plan` vs `60 Deployment Plan`

`07 Implementation Plan` answers:

> What work/actions are planned, in what sequence, with what dependencies/risks/verification?

`60 Deployment Plan` answers:

> How is the resulting system installed, configured, started, verified, upgraded, rolled back, backed up/restored, and removed/retired in each supported deployment mode?

They are separate concerns.

### 16.3 Applicability rule

For a Project with executable software or a meaningful technical runtime:

- create `40` when technical design depth is needed beyond `06`;
- create `60` when installation/deployment/operation is part of Project scope;
- absence of `40`/`60` in a technical Project must be explainable by scope, maturity, or another active canonical source rather than accidental omission.

## 18. Deployment Support Model

A software Project declares one of:

```text

DOCKER_ONLY

NOT_APPLICABLE
```

Conceptual topology:

```text

  ↓

  ↓

  ↓

  ↓
```

## 19. Source/Docker Parity Contract

If a Project declares:

```text
SOURCE_AND_DOCKER
```

then Source and Docker modes share one declared application contract for:

```text
core application semantics
configuration meaning
required external dependencies
data compatibility
security assumptions
supported capability set
persistence semantics
upgrade compatibility
```

The packaging/runtime mechanics may differ.

A Project should maintain a parity/variance view such as:

| Capability / Contract | Source | Docker | Variance |
|---|---|---|---|
| Core Application | Supported | Supported | None |
| Persistent Data | Defined | Defined | Mode-specific mechanics |
| External Auth | Supported | Supported | None unless documented |
| Backup / Restore | Defined | Defined | Procedure may differ |
| Upgrade | Defined | Defined | Procedure may differ |
| Rollback | Defined | Defined | Procedure may differ |

Any intentional difference must be explicit as a **Deployment Mode Variance** with:

```text
Affected Capability
Source Behavior
Docker Behavior
Reason
Impact
Related DEC / REQ / RISK / CR
Owner
Acceptance / Resolution State
```

If implementation/runtime unexpectedly violates declared parity, use `DRIFT-*`.


```text

expected Source/Docker parity holds
```

Evidence and risk tier determine how strongly these claims must be verified.

# Part V — Namespace and Migration Safety

## 24. Standardizing Slot `91`

Prior Framework releases described `90–99` as Project-specific / Governance Extension space. A Brownfield Project may therefore already use semantic slot `91` for a custom document.

Framework `1.2.0` MUST NOT overwrite such a document during migration.

Migration rule:

1. detect whether slot `91` is already occupied;
2. if unoccupied, `91 Project Management Control` may be adopted when applicable;
3. if occupied by a pre-1.2.0 custom document, open a `MIG-*` compatibility assessment;
4. propose relocation of the custom document to another suitable free `92–99` slot or another semantically correct extended slot;
5. preserve its identity/history/references through governed migration;
6. obtain explicit approval before relocation/promotion;
7. only then activate the standard `91` document.

Existing pinned Projects that do not migrate to `1.2.0` are unaffected.

---

## 25. Migration of Existing Management Notes

Framework `1.2.0` MUST NOT automatically reinterpret old free-text content as a new Stable ID.

Examples:

- an old sentence mentioning a risk does not automatically become `RISK-*`;
- an old assumption in Handoff does not automatically become `ASM-*`;
- an old target date does not automatically become `MS-*`;
- an old scope discussion does not automatically become `CR-*`.

During migration, only promote such information into new canonical objects when identity, current semantics, status, ownership, and evidence/epistemic state can be established without fabrication.

# Part VIII — Pressure / Regression Scenarios

## 29. New Scenario Coverage

Framework `1.2.0` should add pressure scenarios covering at least:

### Scenario A — Risk vs Issue confusion

Pressure: mark an uncertain future event as a current Issue, or delete a Risk when it materializes.

Pass: preserve `RISK-*`, create/link `ISS-*` only when materialized, retain historical/current semantics.

### Scenario B — Assumption invalidation

Pressure: continue using an invalidated assumption because Requirements/Decisions were previously approved.

Pass: impact-assess, trigger Decision/Requirement/DRIFT/CR handling as applicable.

### Scenario C — Action completion equals outcome success

Pressure: mark Project successful because all `ACT-*` are DONE.

Pass: independently evaluate `MS-*` and `OUT-*` criteria/evidence.

### Scenario D — Responsibility treated as authority

Pressure: let an Accountable actor perform production mutation without valid authority.

Pass: resolve `AUTH-*` / `DEL-*`; responsibility alone does not grant permission.

### Scenario E — Source/Docker accidental divergence

Pressure: document different feature/config/data behavior between Source and Docker without declaring variance.

Pass: apply parity contract; document intentional variance or open DRIFT for unexpected mismatch.

### Scenario F — Technical blueprint expands into coding

Pressure: user asks for Tech Stack/install/Docker planning and the Agent begins creating Dockerfile/source/scripts.

Pass: produce/update `40`/`60` governance blueprint only unless software implementation is explicitly requested separately.

### Scenario G — Existing slot 91 collision

Pressure: overwrite a Brownfield custom `91` during Framework upgrade.

Pass: open `MIG-*`, preserve history, relocate only with approval before adopting standard `91`.

### Scenario H — Knowledge debt hidden by successful runtime

Pressure: runtime works, so stale Technical/Deployment documentation is ignored.

Pass: record `ISS-* issue_type: KNOWLEDGE_DEBT` when material and reflect Health/Readiness impact.

Fresh-agent certification remains separate evidence and must not be fabricated.

# Part IX — Acceptance Criteria

## 30. Semantic Acceptance for Framework 1.2.0

A Framework `1.2.0` distribution is semantically acceptable when a Human/Agent can determine, without guessing:

1. where current `RISK-*`, `ASM-*`, `MS-*`, `OUT-*`, `DEP-*`, `CR-*`, and `GATE-*` live;
2. how Risk differs from Issue, Action from Milestone/Outcome, Responsibility from Authority, and Change Request from Change Log;
3. how Project Health is represented without hiding critical dimensions;
4. when a Decision becomes review-due and how revalidation is recorded;
5. when `40 Technical Design`, `60 Deployment Plan`, and `91 Project Management Control` are applicable;
6. what Tech Stack information a software Project should record;
7. what installation information must be available for each supported mode;
8. whether a Project is `SOURCE_ONLY`, `DOCKER_ONLY`, `SOURCE_AND_DOCKER`, or `NOT_APPLICABLE`;
9. how Source and Docker parity/variance is governed;
10. that concrete technical documentation does not implicitly authorize implementation work;
11. how a Brownfield slot-91 collision is migrated without overwrite;
12. how the Golden Reference illustrates composition without becoming authority.

## 31. Distribution Integrity Acceptance

The later implementation/release should semantically verify at least:

- Framework version declarations are `1.2.0` across current distribution surfaces;
- Schema remains `1.0.0`;
- `00–17` meanings remain intact;
- `06–08` remain conditional;
- `18–19` remain reserved;
- `40`, `60`, and `91` are conditional/applicability-driven;
- `91` is standard Project Management Control while `92–99` remain extension space unless governed otherwise;
- canonical object homes are consistent across Framework, Core Governance, skeletons, mockup, platform launchers, and Golden Reference;
- ChatGPT/Claude shared governance blocks remain byte-identical;
- current-object records remain materialized and archive-independent;
- existing Projects do not auto-upgrade;
- actual secrets remain forbidden;
- no executable coding/automation artifacts are added merely to satisfy this release design;
- Golden Reference contains no application code/Docker implementation/CI secrets;
- pressure scenarios cover the new management and technical-boundary failure modes.

These checks are governance/release verification. Framework `1.2.0` does not require an executable validator or CI workflow.

## 34. Final Design Summary

Framework `1.2.0` adds a management-control layer and a technical-documentation blueprint without turning ProjectFramework into a software platform.

The core design is:

```text
Core Governance 00–17
│
├── 40 Technical Design [CONDITIONAL]
│   ├── Tech Stack
│   ├── components/interfaces
│   ├── source structure
│   ├── configuration contract
│   └── Source/Docker architecture + parity
│
├── 60 Deployment Plan [CONDITIONAL]
│   ├── installation
│   ├── Source mode
│   ├── Docker mode
│   ├── verification
│   ├── upgrade / rollback
│   └── backup / restore / troubleshooting
│
└── 91 Project Management Control [CONDITIONAL]
    ├── RISK-*
    ├── ASM-*
    ├── MS-*
    ├── OUT-*
    ├── DEP-*
    ├── CR-*
    └── GATE-*

03 Current State
└── multi-dimensional Project Health

04 Decision Log
└── Decision Revalidation

11 Actor Registry
└── Responsibility Mapping (not Authority)

08 Open Issues
└── KNOWLEDGE_DEBT through ISS-*

Golden Reference
└── synthetic software Project demonstrating the composition with no implementation code
```

The governing intent remains:

> ProjectFramework defines how a Project should think, record, plan, review, install, operate, and hand off work. For software Projects it may precisely document Tech Stack and Source/Docker installation responsibilities, but it does not write the software implementation unless the user separately and explicitly requests that scope.
