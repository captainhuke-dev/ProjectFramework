# Framework 1.2.4 — Project Location Binding, Chat Closure Consistency, and Mandatory Response Close Design

## 1. Purpose

Framework `1.2.4` closes three continuation/reliability gaps without changing Project Source Schema `1.0.0` or adding a Stable-ID family:

1. a Project needs a durable declaration of **which GitHub repository and Google Drive project location belong to it** so an Agent does not infer the working location from chat memory, recent connector activity, search ranking, or another accessible Project;
2. `Next Action` and `Chat` need a deterministic consistency contract so `ไม่มีขั้นตอนถัดไป` cannot pair with `CONTINUE_CURRENT_CHAT`;
3. the mandatory response close should use clearer bracketed field labels while preserving the existing two-heading structure and canonical lifecycle vocabulary.

This is governance/documentation scope only. It adds no connector implementation, synchronization service, scheduler, bot, validator, CI workflow, or background memory system.

## 2. Non-goals

Framework `1.2.4` MUST NOT:

- make upstream `ProjectFramework` live authority for initialized Projects;
- replace Project-local `FRAMEWORK-001` authority;
- equate Project Location Binding with `Canonical Implementation Source`;
- create a second branch/integration authority that competes with Framework `1.2.2` **Canonical Integration Target** semantics;
- treat a Drive display path as stable identity when folder/file ID or canonical URL is available;
- duplicate source-native authoritative content between GitHub and Drive;
- automatically create Drive folders/files merely because a binding field exists;
- force every Project to use GitHub or Drive;
- store secrets, access tokens, or connector credentials;
- make `START_NEW_CHAT` mandatory merely because a response is long;
- let `START_NEW_CHAT` bypass the existing Material-work persistence gate;
- let connector discovery, recent activity, or search results silently rewrite Project Location Binding.

## 3. Root Design Principle

> **Resolve durable Project identity and location before relying on temporary session context.**

Active local `FRAMEWORK-001` is the canonical governance home for declared working locations. Platform launchers instruct the Agent to resolve that local binding; they do not copy Project-specific repository/Drive values and therefore do not become a second source of truth.

Project Location Binding is **fail-closed for Material mutation**: uncertainty may permit discovery/read-only inspection, but it does not silently authorize a shared-state write to an unbound target.

## 4. Project Location Binding

### 4.1 Canonical home and mutation authority

Add **Project Location Binding** to active `00 Project Source Framework` / `FRAMEWORK-001`.

The binding is root-level because it must be available during session preflight before Material connector mutation. `03 Current State` and `09 Handoff` MAY reference it but MUST NOT keep an independent authoritative copy.

Because the binding is part of `FRAMEWORK-001`, **changing an active Project Location Binding is a Root Governance mutation**. Therefore:

1. an Agent MUST NOT rewrite the binding merely because it observes another repository/folder, follows recent activity, or receives different connector search results;
2. changing an active binding requires **User Explicit Approval** for the governance change;
3. the change MUST use the existing governed `FRAMEWORK-001` revision → validate → promote → supersede/archive flow;
4. a one-off User Explicit Instruction naming an exact target MAY authorize that specific action when otherwise permitted, but it does **not** persistently change Project Location Binding unless the user separately approves the Root Governance revision;
5. observations that contradict the active binding are evidence/current external state, not automatic authority transfer; material expected-alignment mismatch may use existing `DRIFT-*` semantics.

### 4.2 Distinction from Canonical Implementation Source and Canonical Integration Target

Project Location Binding answers:

```text
Which repository / Drive project container belongs to this Project for connector routing and Project work?
```

Canonical Implementation Source answers:

```text
Which durable source location determines authoritative IMPLEMENTATION Truth for the affected scope?
```

Canonical Integration Target answers:

```text
Which verified Git branch/ref is the current integration target for work governed by Framework 1.2.2 Base Freshness?
```

These concepts may resolve within the same Git repository, but they are not interchangeable:

```text
Repository Location Binding
  ≠ current work branch/worktree
  ≠ Canonical Integration Target
  ≠ Canonical Implementation Source
```

Project Location Binding MUST NOT introduce a new `canonical_branch` or equivalent branch authority. Git integration branch/ref remains governed by existing Framework `1.2.2` **Canonical Integration Target** and Base Freshness semantics. A Project MAY reference that existing contract from Location Binding-related guidance when useful, but MUST NOT duplicate its authority.

### 4.3 Required semantics

The root template should expose semantics equivalent to:

```yaml
project_location_binding:
  github:
    binding_state: "<BOUND | NOT_APPLICABLE | VERIFICATION_REQUIRED>"
    repository: "<OWNER/REPOSITORY_OR_UNKNOWN>"
    repository_url: "<CANONICAL_REPOSITORY_URL_OR_UNKNOWN>"
    project_source_path: "<PROJECT_SOURCE_PATH_OR_UNKNOWN>"
    verification_status: "<VERIFIED | USER_CONFIRMED | VERIFICATION_REQUIRED>"
    last_verified_at: "<ISO8601_OR_UNKNOWN>"

  google_drive:
    binding_state: "<BOUND | NOT_APPLICABLE | VERIFICATION_REQUIRED>"
    project_root_id: "<FOLDER_ID_OR_UNKNOWN>"
    project_root_url: "<CANONICAL_FOLDER_URL_OR_UNKNOWN>"
    display_path: "<OPTIONAL_HUMAN_READABLE_PATH_OR_UNKNOWN>"
    designated_progress_file: "<EXISTING_PROGRESS_MD | PROJECT-PROGRESS.md | NOT_APPLICABLE | UNKNOWN>"
    designated_progress_file_id: "<FILE_ID_OR_UNKNOWN>"
    designated_progress_file_url: "<CANONICAL_FILE_URL_OR_UNKNOWN>"
    verification_status: "<VERIFIED | USER_CONFIRMED | VERIFICATION_REQUIRED>"
    last_verified_at: "<ISO8601_OR_UNKNOWN>"
```

Exact field names may be normalized during implementation, but these meanings are binding requirements of this design.

### 4.4 Binding-state contract — fail closed

Each system resolves explicitly to exactly one of:

```text
BOUND
NOT_APPLICABLE
VERIFICATION_REQUIRED
```

#### `BOUND`

`BOUND` means the Project has enough durable routing identity to identify the Project location for Material connector work.

Minimum routing identity:

```text
GitHub      → repository owner/name OR canonical repository URL
Google Drive → project root folder ID OR canonical folder URL
```

A display name, textual Drive path, recent repository activity, connector ranking, or search result alone is insufficient to claim `BOUND`.

For Material mutation, the intended target MUST match the bound routing identity when comparison is possible. If the target materially disagrees, stop the affected mutation and surface the mismatch.

#### `VERIFICATION_REQUIRED`

`VERIFICATION_REQUIRED` is **fail-closed for Material mutation**.

Allowed by default:

```text
read/search/discovery needed to resolve candidate location
comparison of candidate identities
requesting or receiving user confirmation
```

Blocked by default:

```text
Material write/mutation to an unresolved candidate target
silent promotion of a candidate to Project authority
persistent binding change from observation alone
```

Exception: User Explicit Instruction may identify an exact target for one specific action if that action is otherwise authorized. This action-specific instruction does not convert the persistent binding to `BOUND`; the binding remains `VERIFICATION_REQUIRED` until a governed `FRAMEWORK-001` revision is explicitly approved and promoted.

#### `NOT_APPLICABLE`

`NOT_APPLICABLE` means that connector/system is outside the Project's declared working-location contract.

Material Project work through that system is blocked by default. Enabling it requires an explicitly approved scope/binding change through the governed `FRAMEWORK-001` revision flow. Read-only discovery outside the Project may still occur when the user explicitly requests it, but discovery does not redefine Project authority.

#### Verification status

Unknowns stay `UNKNOWN` / `VERIFICATION_REQUIRED`. `USER_CONFIRMED` is valid when the user supplies a location but connector verification has not yet occurred. `VERIFIED` requires actual source/system verification.

`binding_state: BOUND` with `verification_status: USER_CONFIRMED` is valid when the user has explicitly identified an unambiguous durable routing identity. The distinction is epistemic: the binding can be user-authoritative without falsely claiming connector-level verification.

### 4.5 Google Drive identity and progress

Drive folder/file ID or canonical URL is the stable routing identity when available. `display_path` is descriptive only.

Existing Externalized Working Memory semantics remain unchanged:

- update an existing designated Project progress `.md` at Logical Checkpoints when required;
- if none exists and durable continuation state is required, use one stable `PROJECT-PROGRESS.md` continuation cache;
- the progress file references authoritative Drive artifacts and MUST NOT become a duplicate source of truth.

A designated progress-file pointer is continuation routing metadata; it does not make the progress file authoritative for content owned by another Drive artifact.

### 4.6 Initialized-Project connector preflight

After resolving active local `FRAMEWORK-001`, an Agent MUST read Project Location Binding before Material GitHub or Drive work.

For Material connector work:

1. resolve the applicable system's `binding_state`;
2. if `BOUND`, compare the intended target with the durable routing identity when possible;
3. if `VERIFICATION_REQUIRED`, block Material mutation unless a User Explicit Instruction identifies the exact target for that specific action and the action is otherwise authorized;
4. if `NOT_APPLICABLE`, block Material Project work through that system unless a governed binding/scope revision is approved;
5. never switch repository/Drive root because another accessible location is newer or ranks first in search;
6. if observed target and declared binding materially disagree, stop the affected mutation, disclose the mismatch, and use existing `DRIFT-*` when expected-alignment domains materially conflict;
7. never rewrite Project Location Binding as a side effect of connector discovery;
8. preserve existing Authority/Risk gates independently — Location Binding answers **where**, not **who may mutate what**.

Transient discovery/search may inspect candidate locations when needed, but candidate discovery MUST NOT silently redefine Project authority.

### 4.7 GREENFIELD bootstrap exception

A GREENFIELD Project has no active local `FRAMEWORK-001`, so it cannot resolve a pre-existing Location Binding.

GREENFIELD behavior MUST therefore be:

```text
canonical Framework bootstrap read
→ discovery/read-only inspection of candidate Project locations when needed
→ Preview includes proposed GitHub/Drive Project Location Binding
→ explicit user approval
→ first Material Project-Source write creates active 00 / FRAMEWORK-001 with the approved binding
→ subsequent Material connector work resolves that active binding
```

Discovery before binding MAY read/search candidates, but MUST NOT silently treat a candidate repository or Drive folder as Project authority. Initial/major bootstrap write remains subject to the existing Preview → explicit approval → write gate.

The Preview MUST make each applicable system explicit as `BOUND`, `NOT_APPLICABLE`, or `VERIFICATION_REQUIRED`. If an applicable system remains `VERIFICATION_REQUIRED`, bootstrap may continue only where existing Framework gates allow, but Material mutation through that unresolved system remains fail-closed under §4.4.

### 4.8 Cross-system work

GitHub and Drive remain source-native owners. Binding enables reliable routing and pointers, not replication:

```text
GitHub authoritative artifact ↔ pointer/reference ↔ Drive authoritative artifact
```

Do not create a third canonical copy merely for continuation convenience.

## 5. Chat Closure Consistency

Framework `1.2.1+` defines when `START_NEW_CHAT` is continuation-safe but currently permits the contradictory combination:

```text
Next Action: ไม่มีขั้นตอนถัดไป
Chat: CONTINUE_CURRENT_CHAT
```

Framework `1.2.4` adds these binding invariants:

1. If `[Next Action]` is exactly `ไม่มีขั้นตอนถัดไป`, `[Chat]` MUST be `START_NEW_CHAT`.
2. If `[Chat]` is `CONTINUE_CURRENT_CHAT`, `[Next Action]` MUST contain one concrete continuation action and MUST NOT be `ไม่มีขั้นตอนถัดไป`.
3. `PERSISTENCE_PENDING` MUST pair with `CONTINUE_CURRENT_CHAT` and a concrete persistence/recovery Next Action. `PERSISTENCE_PENDING + ไม่มีขั้นตอนถัดไป` is invalid.
4. `START_NEW_CHAT` MAY still have a concrete Next Action when Material state is durably persisted and the next unit of work is continuation-safe from external state.
5. `START_NEW_CHAT` is a recommendation that the current chat is safe/preferable to close; it does not claim the platform forces navigation.

Decision matrix:

| Situation | Next Action | Chat |
|---|---|---|
| Workstream complete; no pending work | `ไม่มีขั้นตอนถัดไป` | `START_NEW_CHAT` |
| More work depends on current conversational context | one concrete action | `CONTINUE_CURRENT_CHAT` |
| Waiting for user approval/input in this workflow | one concrete approval/input action | `CONTINUE_CURRENT_CHAT` |
| Required Material persistence failed/pending | one concrete persistence/recovery action | `CONTINUE_CURRENT_CHAT` |
| State persisted; next work cleanly resumable from durable sources | one concrete action | `START_NEW_CHAT` |

Do not impose the reverse rule that every concrete Next Action requires `CONTINUE_CURRENT_CHAT`.

## 6. Mandatory Response Close Format

Every response continues to end with exactly two headings, in order, with nothing after the second section:

```text
### ทำอะไรไป?

<concise statement of what was done or determined>

### และถัดไปคืออะไร?

[Next Action]: <one exact next action or ไม่มีขั้นตอนถัดไป>

[Chat]: CONTINUE_CURRENT_CHAT | START_NEW_CHAT

[Reason]: <concise reason>

[Required Read]: <canonical locations or ไม่มี>
```

Each bracketed field is a separate Markdown paragraph with a blank line between fields.

Canonical lifecycle tokens remain exactly:

```text
CONTINUE_CURRENT_CHAT
START_NEW_CHAT
```

A renderer MAY escape underscores for Markdown display (for example `CONTINUE\_CURRENT\_CHAT`), but backslashes are display syntax only and are not part of the canonical token.

## 7. Platform Launcher Contract

`CHATGPT-PROJECT-INSTRUCTIONS.md` and `CLAUDE-PROJECT-INSTRUCTIONS.md` MUST remain byte-identical between the shared contract markers.

The launcher carries compact rules equivalent to:

```text
Resolve active local FRAMEWORK-001 first. Read its Project Location Binding before Material GitHub/Drive work. Do not infer working repo/Drive root from chat memory, recent activity, search ranking, or other accessible Projects. VERIFICATION_REQUIRED is fail-closed for Material mutation; binding changes require explicit Root Governance approval.
```

and:

```text
ไม่มีขั้นตอนถัดไป → START_NEW_CHAT. CONTINUE_CURRENT_CHAT requires one concrete Next Action. PERSISTENCE_PENDING requires CONTINUE_CURRENT_CHAT + a persistence/recovery Next Action.
```

The launcher MUST NOT encode a competing canonical branch field. Existing Canonical Integration Target semantics remain in the pinned Framework sources.

The complete ChatGPT/Claude instruction artifact MUST remain `<=4,500` Unicode characters. Wording may be compressed, but higher-priority governance semantics MUST NOT be removed merely to fit the limit.

## 10. Pressure Scenarios / Acceptance Criteria

Implementation must cover at least:

1. **Wrong GitHub repo from recent activity:** bound `repo-A`; newer `repo-B` is accessible → Agent keeps `repo-A` unless binding/scope changes explicitly.
2. **Wrong Drive folder from ranking:** bound folder ID `A`; similarly named folder `B` ranks first → no silent switch.
3. **Unknown binding / fail closed:** system is `VERIFICATION_REQUIRED` → discovery/read-only candidate inspection allowed; Material mutation blocked unless User Explicit Instruction identifies the exact target for that specific action.
4. **One-off target is not persistent authority:** user names exact target for one action while binding is `VERIFICATION_REQUIRED` → action may proceed if otherwise authorized; persistent binding remains unchanged until explicit `FRAMEWORK-001` revision approval/promotion.
5. **NOT_APPLICABLE:** Material Project work through that connector is blocked until approved Root Governance binding/scope change.
6. **BOUND minimum identity:** GitHub `BOUND` lacks owner/repo and canonical URL, or Drive `BOUND` lacks folder ID and canonical URL → binding is invalid/incomplete for Material routing and must not be treated as resolved.
7. **Binding mismatch:** intended Material target differs from declared binding → stop affected mutation; disclose; use `DRIFT-*` when materially appropriate.
8. **No silent Root Governance mutation:** connector discovers a more likely repo/folder → Agent may report/propose change but MUST NOT update binding without User Explicit Approval + governed `FRAMEWORK-001` revision flow.
9. **Branch authority remains separate:** repository is bound, but current feature branch differs from Canonical Integration Target → Location Binding does not override Framework `1.2.2` Base Freshness/Canonical Integration Target semantics.
10. **GREENFIELD:** discovery may occur before local `00`, but first Material Project-Source write follows approved Preview and writes the approved binding states into active `FRAMEWORK-001`.
11. **No next action:** `ไม่มีขั้นตอนถัดไป` → `START_NEW_CHAT`.
12. **Invalid continue close:** `CONTINUE_CURRENT_CHAT + ไม่มีขั้นตอนถัดไป` is invalid.
13. **Persistence pending:** `PERSISTENCE_PENDING` → `CONTINUE_CURRENT_CHAT` + concrete recovery action.
14. **Fresh-chat continuation:** persisted durable state may use `START_NEW_CHAT` + concrete Next Action + Required Read.
15. **Response format:** `[Next Action]:`, `[Chat]:`, `[Reason]:`, `[Required Read]:` appear as four separate paragraphs.
16. **Launcher parity/size:** shared marker content is byte-identical and each complete launcher is `<=4,500` Unicode characters.

## 11. Migration and Backward Compatibility

Framework `1.2.4` migration MUST NOT invent Project locations.

For a migrating initialized Project:

1. preserve active `FRAMEWORK-001` until migration approval/promotion completes;
2. inventory known GitHub/Drive locations from actual Project sources and user-confirmed context;
3. classify each system `BOUND`, `NOT_APPLICABLE`, or `VERIFICATION_REQUIRED`;
4. require minimum durable routing identity before classifying a system `BOUND`;
5. record observed IDs/URLs only; never fabricate repo identity, Drive folder ID, or file ID;
6. do not create or migrate a `canonical_branch` field; preserve existing Canonical Integration Target semantics separately;
7. revise `FRAMEWORK-001` through governed revision/supersede/archive flow with User Explicit Approval;
8. make continuation documents reference the root binding rather than duplicate location authority;
9. preserve Canonical Implementation Source semantics independently;
10. validate fail-closed behavior, Project Source integrity, and launcher behavior after promotion.

A Project that does not use Drive is `NOT_APPLICABLE`, not defective. A Project that materially relies on Drive but cannot resolve its root is `VERIFICATION_REQUIRED` for the affected connector scope and cannot perform Material Drive mutation by default.

Existing initialized Projects that do not migrate remain governed by their prior local pin and are not silently assigned new binding values.

The design is complete when this revision is user-reviewed and approved.

Framework `1.2.4` implementation is complete only when:

- Location Binding is consistent across normative/current starter surfaces;
- GitHub and Drive are independently explicit as `BOUND`, `NOT_APPLICABLE`, or `VERIFICATION_REQUIRED`;
- `VERIFICATION_REQUIRED` and `NOT_APPLICABLE` fail closed for Material mutation as specified;
- `BOUND` requires sufficient durable routing identity rather than name/ranking inference;
- GREENFIELD bootstrap has a safe pre-binding discovery path and approved first-write binding;
- Project-specific values live in local `FRAMEWORK-001`, not platform launchers;
- active binding changes require User Explicit Approval and governed Root Governance revision/promotion;
- one-off action-specific target instructions do not silently persist as new binding authority;
- Location Binding is not conflated with Canonical Implementation Source;
- Location Binding does not create a competing `canonical_branch`; Canonical Integration Target remains governed by Framework `1.2.2`;
- Material routing does not rely on chat memory/recent activity/search ranking;
- `ไม่มีขั้นตอนถัดไป → START_NEW_CHAT` is enforced;
- `CONTINUE_CURRENT_CHAT` always has a concrete Next Action;
- `PERSISTENCE_PENDING` cannot pair with no next action or `START_NEW_CHAT`;
- response-close fields use the approved bracketed display format;
- launcher shared contracts remain byte-identical and each launcher stays `<=4,500` Unicode characters;
- Framework is `1.2.4`, Schema remains `1.0.0`, and existing Projects remain non-auto-upgrading;
- historical amendments/specs are not rewritten.

## 14. Approved Design Summary

```text
active local FRAMEWORK-001
  └─ Project Location Binding
       ├─ GitHub repository routing boundary
       └─ Google Drive project-root/progress pointer boundary

Binding states
  → BOUND = sufficient durable routing identity
  → VERIFICATION_REQUIRED = discovery/read allowed; Material mutation fail-closed
  → NOT_APPLICABLE = Material connector Project work disabled

Binding authority
  → discovery/recency/search never rewrites binding
  → persistent change requires User Explicit Approval
  → revise/promote FRAMEWORK-001 through governed flow
  → one-off exact-target instruction ≠ persistent binding change

Git semantics
  → repository binding ≠ current work branch
  → repository binding ≠ Canonical Integration Target
  → repository binding ≠ Canonical Implementation Source

GREENFIELD
  → discover candidates read-only as needed
  → Preview proposed binding states/identities
  → explicit approval
  → create active 00 with binding

Material connector work
  → resolve binding state
  → fail closed when unresolved/not applicable
  → verify target when possible
  → preserve independent Authority/Risk gates
  → persist to source-native owner

Response close
  → ไม่มีขั้นตอนถัดไป => START_NEW_CHAT
  → CONTINUE_CURRENT_CHAT => concrete Next Action
  → PERSISTENCE_PENDING => CONTINUE_CURRENT_CHAT + recovery action
  → bracketed field labels for display
```

This design strengthens continuation reliability without creating a new source of truth, branch authority, automation layer, or schema namespace.
