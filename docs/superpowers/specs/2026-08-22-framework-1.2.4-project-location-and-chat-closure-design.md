# Framework 1.2.4 — Project Location Binding, Chat Closure Consistency, and Mandatory Response Close Design

## 1. Purpose

Framework `1.2.4` closes three related continuation/reliability gaps without changing Project Source Schema `1.0.0` or introducing a new Stable-ID family:

1. a Project needs a durable, explicit declaration of **which GitHub repository and Google Drive project location belong to that Project** so an Agent does not infer the working location from chat memory, recent connector activity, search ranking, or another accessible Project;
2. `Next Action` and `Chat` lifecycle output need a deterministic consistency rule so `ไม่มีขั้นตอนถัดไป` cannot be paired with `CONTINUE_CURRENT_CHAT`;
3. the mandatory response close should use clearer bracketed field labels while preserving the existing two-heading structure and canonical lifecycle vocabulary.

This release is governance/documentation scope only. It adds no connector implementation, synchronization service, scheduler, bot, validator, CI workflow, or background memory system.

## 2. Non-goals

Framework `1.2.4` MUST NOT:

- make upstream `ProjectFramework` a live authority for initialized Projects;
- replace Project-local `FRAMEWORK-001` authority;
- equate Project Location Binding with `Canonical Implementation Source`;
- treat a Google Drive display path as a stable identity when folder/file IDs or canonical URLs are available;
- duplicate source-native authoritative content between GitHub and Drive;
- automatically create Google Drive folders/files merely because a binding field exists;
- force every Project to use GitHub or Google Drive;
- store secrets, access tokens, connector credentials, or private authentication material;
- make `START_NEW_CHAT` mandatory merely because a response is long;
- allow `START_NEW_CHAT` to bypass the existing persistence gate for Material Project Work.

## 3. Design Principle

The release uses one root principle:

> **Resolve durable Project identity and location before relying on temporary session context.**

The active local `FRAMEWORK-001` is the canonical governance home for the Project's declared working locations. Platform launchers only instruct the Agent to resolve that local binding; they do not copy Project-specific repository/Drive values and therefore do not become a second source of truth.

## 4. Project Location Binding

### 4.1 Canonical Home

Add a **Project Location Binding** section to active `00 Project Source Framework` / `FRAMEWORK-001`.

The binding is root-level Project governance because it must be available during bootstrap/session preflight before connector mutation. `03 Current State` and `09 Handoff` MAY reference the root binding when continuation needs to surface it, but they MUST NOT maintain an independent authoritative copy.

### 4.2 Semantic distinction from Canonical Implementation Source

Project Location Binding answers:

```text
Which repository / Drive project container belongs to this Project for connector routing and Project work?
```

Canonical Implementation Source answers:

```text
Which durable source location determines authoritative IMPLEMENTATION Truth for the affected scope?
```

These concepts may point to the same Git repository in a software Project, but they are not semantically interchangeable. Project Location Binding is a routing/work-boundary contract; Canonical Implementation Source remains an Implementation Truth contract governed by Framework `1.2.3`.

### 4.3 Recommended representation

The root template should expose a structure equivalent to:

```yaml
project_location_binding:
  github:
    binding_state: "<BOUND | NOT_APPLICABLE | VERIFICATION_REQUIRED>"
    repository: "<OWNER/REPOSITORY_OR_UNKNOWN>"
    repository_url: "<CANONICAL_REPOSITORY_URL_OR_UNKNOWN>"
    canonical_branch: "<BRANCH_OR_UNKNOWN>"
    project_source_path: "<PROJECT_SOURCE_PATH_OR_UNKNOWN>"
    verification_status: "<VERIFIED | USER_CONFIRMED | VERIFICATION_REQUIRED>"
    last_verified_at: "<ISO8601_OR_UNKNOWN>"

  google_drive:
    binding_state: "<BOUND | NOT_APPLICABLE | VERIFICATION_REQUIRED>"
    project_root_id: "<FOLDER_ID_OR_UNKNOWN>"
    project_root_url: "<CANONICAL_FOLDER_URL_OR_UNKNOWN>"
    display_path: "<OPTIONAL_HUMAN_READABLE_PATH_OR_UNKNOWN>"
    designated_progress_file: "<EXISTING_PROGRESS_MD | PROJECT-PROGRESS.md | NOT_APPLICABLE | UNKNOWN>"
    designated_progress_file_id: "<FILE_ID_OR_UNKNOWN>"
    designated_progress_file_url: "<CANONICAL_FILE_URL_OR_UNKNOWN>"
    verification_status: "<VERIFIED | USER_CONFIRMED | VERIFICATION_REQUIRED>"
    last_verified_at: "<ISO8601_OR_UNKNOWN>"
```

Exact field naming may be adjusted during implementation for consistency with existing template style, but the semantics above are binding requirements of this design.

### 4.4 Applicability and uncertainty

A Project does not need to use both systems. Each system MUST explicitly resolve to one of:

```text
BOUND
NOT_APPLICABLE
VERIFICATION_REQUIRED
```

Unknown values remain `UNKNOWN` / `VERIFICATION_REQUIRED`; Agents MUST NOT guess repository identity, branch, Drive folder, file ID, or path merely to make the record complete.

`USER_CONFIRMED` remains valid when the user explicitly supplies a location but connector-level verification has not yet occurred. `VERIFIED` requires actual verification against the relevant system/source.

### 4.5 Google Drive identity

For Drive, canonical folder/file ID or canonical URL is the stable routing identity when available. A human-readable `display_path` is descriptive only because folders may be renamed or reorganized without preserving a unique textual path contract.

The existing Externalized Working Memory rule remains unchanged:

- if an existing designated progress `.md` exists, update it at Logical Checkpoints when required;
- if none exists and durable continuation state is required, use one stable `PROJECT-PROGRESS.md` continuation cache;
- that progress file references authoritative Drive artifacts and MUST NOT become a duplicate source of truth.

### 4.6 Session and connector preflight

After resolving active local `FRAMEWORK-001`, an Agent MUST read Project Location Binding before Material GitHub or Google Drive work.

For Material connector reads/writes that can affect Project continuation or shared state:

1. resolve the declared binding;
2. compare the intended connector target with the binding when verification is possible;
3. operate only within the declared Project location unless the user explicitly changes scope or the Framework-governed binding is revised;
4. never switch repository/Drive root merely because another accessible location has more recent activity or appears first in search results;
5. if observed target and declared binding materially disagree, stop the affected mutation, disclose the mismatch, and use existing `DRIFT-*` semantics when the domains are expected to align;
6. if the binding cannot be verified, preserve `VERIFICATION_REQUIRED` and avoid fabricating certainty.

Transient discovery/search may inspect candidate locations when needed to resolve ambiguity, but candidate discovery MUST NOT silently redefine Project authority.

### 4.7 Cross-system work

GitHub and Drive remain source-native owners. The binding allows reliable routing and cross-references, not replication.

```text
GitHub authoritative artifact ↔ pointer/reference ↔ Drive authoritative artifact
```

Do not create a third canonical copy merely to make continuation easier.

## 5. Chat Closure Consistency

### 5.1 Problem

Framework `1.2.1+` defines when `START_NEW_CHAT` is continuation-safe, especially after persistence, but does not currently define the inverse consistency rule between `Next Action` and `Chat`. This permits semantically contradictory closes such as:

```text
Next Action: ไม่มีขั้นตอนถัดไป
Chat: CONTINUE_CURRENT_CHAT
```

### 5.2 Binding invariants

Framework `1.2.4` adds these rules:

1. **No next action means close-safe chat recommendation.**
   If `[Next Action]` is exactly `ไม่มีขั้นตอนถัดไป`, `[Chat]` MUST be `START_NEW_CHAT`.

2. **Continue-current-chat requires actionable continuation.**
   If `[Chat]` is `CONTINUE_CURRENT_CHAT`, `[Next Action]` MUST contain one concrete continuation action and MUST NOT be `ไม่มีขั้นตอนถัดไป`.

3. **Persistence pending always has recovery work.**
   `PERSISTENCE_PENDING` MUST pair with `CONTINUE_CURRENT_CHAT` and a concrete persistence/recovery Next Action. `PERSISTENCE_PENDING + ไม่มีขั้นตอนถัดไป` is invalid.

4. **START_NEW_CHAT may still have a concrete Next Action.**
   When Material state is durably persisted and the next unit of work is continuation-safe from external state, the response MAY recommend `START_NEW_CHAT` while still naming a concrete Next Action and Required Read.

5. **START_NEW_CHAT is a recommendation, not forced UI navigation.**
   It means the current chat is safe/preferable to close for continuation quality. It does not claim the platform forcibly closes or creates a chat.

### 5.3 Decision matrix

| Situation | Next Action | Chat |
|---|---|---|
| Workstream complete; no pending work | `ไม่มีขั้นตอนถัดไป` | `START_NEW_CHAT` |
| More work depends on current conversational context | one concrete action | `CONTINUE_CURRENT_CHAT` |
| Waiting for user approval/input in this workflow | one concrete approval/input action | `CONTINUE_CURRENT_CHAT` |
| Required Material persistence failed/pending | one concrete persistence/recovery action | `CONTINUE_CURRENT_CHAT` |
| State is persisted and next work is cleanly resumable from durable sources | one concrete action | `START_NEW_CHAT` |

The Framework MUST NOT impose the reverse rule that every concrete Next Action requires `CONTINUE_CURRENT_CHAT`; safe fresh-chat continuation remains an intended capability.

## 6. Mandatory Response Close Format

### 6.1 Required display structure

Every response continues to end with exactly two headings in this order, with nothing after the second section:

```text
### ทำอะไรไป?

<concise statement of what was done or determined>

### และถัดไปคืออะไร?

[Next Action]: <one exact next action or ไม่มีขั้นตอนถัดไป>

[Chat]: CONTINUE_CURRENT_CHAT | START_NEW_CHAT

[Reason]: <concise reason>

[Required Read]: <canonical locations or ไม่มี>
```

Each bracketed field MUST be a separate Markdown paragraph with a blank line between fields.

### 6.2 Canonical token vs Markdown escaping

Canonical lifecycle values remain exactly:

```text
CONTINUE_CURRENT_CHAT
START_NEW_CHAT
```

A renderer MAY escape underscores for Markdown display if necessary (for example `CONTINUE\_CURRENT\_CHAT`), but the semantic token itself remains unescaped. Backslashes are presentation syntax, not part of the canonical vocabulary.

### 6.3 Compatibility

The two existing Thai headings remain unchanged. Only field-label display changes from plain labels to bracketed labels. Existing semantic meanings of Next Action, Reason, and Required Read remain intact except for the new Chat Closure Consistency rules.

## 7. Platform Launcher Contract

`CHATGPT-PROJECT-INSTRUCTIONS.md` and `CLAUDE-PROJECT-INSTRUCTIONS.md` MUST remain byte-identical between the shared contract markers.

The launcher should carry only compact rules such as:

```text
Resolve active local FRAMEWORK-001 first. Read its Project Location Binding before Material GitHub/Drive work. Do not infer working repo/Drive root from chat memory, recent activity, search ranking, or other accessible Projects.
```

and compact closure semantics such as:

```text
ไม่มีขั้นตอนถัดไป → START_NEW_CHAT. CONTINUE_CURRENT_CHAT requires one concrete Next Action. PERSISTENCE_PENDING requires CONTINUE_CURRENT_CHAT + a persistence/recovery Next Action.
```

The complete ChatGPT/Claude instruction artifact MUST remain `<=4,500` Unicode characters. Implementation may compress wording elsewhere but MUST NOT remove higher-priority governance semantics merely to fit the size limit.

## 8. Framework Release and Schema

Target release:

```text
Project Source Framework: 1.2.4
Project Source Schema:    1.0.0
```

Rationale for no schema bump:

- no new semantic slot;
- no new Stable-ID namespace;
- no object-home relocation;
- no change to the Current Reconstructable Snapshot model;
- new root governance fields/sections and lifecycle consistency rules remain backward-compatible within the existing document model.

Existing initialized Projects do not auto-upgrade. They remain governed by their locally pinned Framework version until a governed `MIG-*` upgrade is explicitly approved.

## 10. Pressure Scenarios / Acceptance Tests

At minimum, the release should add or update pressure scenarios for:

### 10.1 Wrong GitHub repository from recent activity

Given a Project bound to `owner/repo-A`, the connector can access `repo-B` and `repo-B` has newer activity. The Agent MUST continue to treat `repo-A` as the Project working repository unless scope/binding is explicitly changed.

### 10.2 Wrong Drive folder from search ranking

Given a Project bound to Drive folder ID `A`, search returns similarly named folder `B` first. The Agent MUST NOT silently use `B` for Material work.

### 10.3 Binding unknown

If GitHub or Drive is `VERIFICATION_REQUIRED`, the Agent may discover candidates but MUST NOT promote one to verified authority without evidence/user confirmation appropriate to the source.

### 10.4 Binding mismatch

Declared repo/Drive root differs from the intended Material write target. The Agent stops the affected mutation, surfaces the mismatch, and applies `DRIFT-*` when an expected-alignment truth mismatch is material.

### 10.5 No next action

A completion response with `ไม่มีขั้นตอนถัดไป` MUST output `START_NEW_CHAT`.

### 10.6 Invalid continue-current-chat close

`CONTINUE_CURRENT_CHAT + ไม่มีขั้นตอนถัดไป` MUST be rejected as semantically inconsistent.

### 10.7 Persistence pending

`PERSISTENCE_PENDING` MUST output `CONTINUE_CURRENT_CHAT` and one concrete persistence/recovery Next Action.

### 10.8 Fresh-chat continuation with work remaining

When durable continuation state exists and a clean context is preferable, `START_NEW_CHAT` MAY pair with a concrete Next Action and Required Read.

### 10.9 Response close formatting

Both platform launchers and relevant Framework examples use:

```text
[Next Action]:
[Chat]:
[Reason]:
[Required Read]:
```

as four separate paragraphs under the second mandatory heading.

### 10.10 Launcher parity and size

Shared contract text between markers is byte-identical across ChatGPT and Claude launchers, and each complete instruction artifact is `<=4,500` Unicode characters.

## 11. Migration and Backward Compatibility

Framework `1.2.4` migration MUST NOT invent Project locations for existing Projects.

For a migrating initialized Project:

1. preserve its current active `FRAMEWORK-001` until migration approval/promotion completes;
2. inventory known GitHub/Drive locations from actual Project sources and user-confirmed context;
3. classify each binding as `BOUND`, `NOT_APPLICABLE`, or `VERIFICATION_REQUIRED`;
4. use observed IDs/URLs where available; never fabricate Git repository identity, branch, Drive folder ID, or file ID;
5. revise active `FRAMEWORK-001` through governed revision/supersede/archive flow;
6. update continuation references to point to the root binding rather than maintain duplicate location authority;
7. preserve existing `Canonical Implementation Source` semantics independently;
8. validate launcher/Project Source behavior after promotion.

A missing Drive binding in a Project that does not use Drive is `NOT_APPLICABLE`, not a readiness defect. A Project that materially relies on Drive but cannot yet resolve the root is `VERIFICATION_REQUIRED` for the affected connector scope.

## 14. Approved Design Summary

The approved direction is:

```text
active local FRAMEWORK-001
  └─ Project Location Binding
       ├─ GitHub working repository boundary
       └─ Google Drive project-root/progress pointer boundary

Material connector work
  → resolve binding
  → verify target when possible
  → do not infer/switch from chat memory or recency
  → persist to source-native owner

Response close
  → ไม่มีขั้นตอนถัดไป => START_NEW_CHAT
  → CONTINUE_CURRENT_CHAT => concrete Next Action
  → PERSISTENCE_PENDING => CONTINUE_CURRENT_CHAT + recovery action
  → bracketed field labels for display
```

This design intentionally strengthens continuation reliability without creating a new source of truth, new automation layer, or new schema namespace.
