## 1. Goal

Framework `1.2.6` resolves the bootstrap-location ambiguity that exists before an Agent can reliably discover active Project governance.

The Framework must distinguish six different location/state questions that are frequently represented by the same repository path in simple Projects but are not the same semantic concept:

1. **Framework Source** — where Framework upstream/bootstrap read-through is located.
2. **Remote Location** — where deterministic remote Project Source discovery starts.
3. **MCP Location** — which Project workspace/root the declared MCP execution surface is expected to target for Material Project work in the applicable environment.
4. **Local Workspace** — where the Project's local durable workspace/root exists in the applicable environment.
5. **File Storage Location** — where durable non-repository Project files/objects are stored, including Google Drive, S3, NAS, or equivalent storage.
6. **current branch/worktree** — the observed Git execution state for the current session; always dynamic and re-verified.

The design must remove the bootstrap paradox without weakening Framework `1.2.4` Project Location Binding or Framework `1.2.5` environment-scoped Local Workspace Binding.

The intended human-readable definitions are deliberately short:

```text
Framework Source = Framework upstream อยู่ที่ไหน
Remote Location = จะเริ่มค้น Project Source จากไหน
MCP Location = Project work ที่ authorize อยู่ที่ไหนสำหรับ MCP environment นี้
Local Workspace = Project local อยู่ที่ไหน
File Storage Location = Project files/objects ที่อยู่นอก repository เก็บแบบ durable อยู่ที่ไหน
current branch/worktree = execution state ปัจจุบัน; ต้องตรวจจาก Git ใหม่
```

## 2. Problem Statement — The Bootstrap Paradox

Framework `1.2.4` and `1.2.5` correctly make active local `FRAMEWORK-001` the canonical home for Project Location Binding and Local Workspace Binding. However, a fresh ChatGPT/Codex/Claude/MCP session may need a deterministic location in order to find that active Project Source in the first place.

Without a bootstrap location declaration, an Agent is tempted to infer the Project from:

- recent repositories;
- connector search ranking;
- an active editor workspace;
- MCP `workspaceId` recency;
- a same-named folder;
- chat memory;
- whichever branch/worktree happens to be checked out.

Those signals are evidence, not authority. The result is a circular dependency:

```text
Need FRAMEWORK-001 to know Project Location Binding
→ but need a deterministic starting location to find FRAMEWORK-001
```

Framework `1.2.6` introduces a **Bootstrap Location Block** to break that circle.

The block is a bootstrap/discovery/routing input. It is not a competing initialized-Project governance root.

## 3. Compatibility and Scope Boundary

Framework `1.2.6` MUST preserve:

- Project Source Schema `1.0.0`;
- existing semantic slots and Stable-ID families;
- Project-local Framework pinning and no auto-upgrade;
- Framework `1.2.1` Externalized Working Memory / Chat Lifecycle semantics;
- Framework `1.2.2` Canonical Integration Target, Base Freshness, `STACKED_WORK`, and Pre-Merge Base Freshness Gate;
- Framework `1.2.3` Canonical Implementation Source / Development Workspace / Runtime Authority semantics;
- Framework `1.2.4` Project Location Binding and `BOUND | NOT_APPLICABLE | VERIFICATION_REQUIRED` fail-closed routing;
- Framework `1.2.5` Environment-Scoped Local Workspace Binding, completion checkpoints, verification/evidence reuse, and response-close completeness;
- existing Authority/Risk/Approval gates independently from location routing.

The release adds no application runtime, automatic repository selector, automatic cloud-storage selector, filesystem watcher, branch switcher, CI/CD system, background process, secret store, or connector credential mechanism.

The location block itself does not grant mutation authority.

## 4. Root Design Principles

### 4.1 Deterministic bootstrap, governed steady state

Before active local `FRAMEWORK-001` can be resolved, the Bootstrap Location Block gives deterministic starting points.

After active local `FRAMEWORK-001` is resolved, initialized-Project governance becomes authoritative for governed Project Location state.

```text
Bootstrap Location Block
  → find/verify Project and execution surfaces
  → resolve active FRAMEWORK-001 when present
  → active FRAMEWORK-001 governs Project Location Binding
```

The bootstrap block remains useful as launcher/environment configuration and mismatch evidence, but it MUST NOT silently override active Root Governance.

### 4.2 Same value does not mean same concept

In ProjectFramework itself, Framework Source, Remote Location, MCP Location, and Local Workspace may all lead to `captainhuke-dev/ProjectFramework` / `E:\GitHub\ProjectFramework`.

That value alignment does not collapse semantics.

### 4.3 Observed Git state is never bootstrap authority

`current branch/worktree` is intentionally dynamic. It MUST be resolved from Git each session and before Material Git work when material.

A Project instruction, handoff, memory, or previous session MAY provide an expected branch/worktree as evidence, but observed Git state wins as the statement of current execution state.

### 4.4 File storage is independent from code/source routing

A Project may validly use:

```text
Git repository → code/configuration
Google Drive → business documents
S3 → datasets/build artifacts
NAS → media/exports/large files
```

The Framework MUST NOT force those locations into one repository path or one connector.

## 5. Canonical Location Semantics

### 5.1 Framework Source

**Question answered:** Where is Framework upstream/bootstrap read-through located?

Typical representation:

```yaml
framework_source:
  repository: "captainhuke-dev/ProjectFramework"
  url: "https://github.com/captainhuke-dev/ProjectFramework"
  bootstrap_ref: "main"
```

Rules:

1. Framework Source is used for Framework bootstrap/read-through and release discovery.
2. It does not identify the consuming Project unless the consuming Project is ProjectFramework itself.
3. It MUST NOT override initialized local Project governance or a pinned Framework version.
4. `bootstrap_ref` is bootstrap/release metadata, not the consuming Project's Canonical Integration Target.
5. Framework Source may be unavailable while an initialized Project remains operable from its valid local pinned Project Source; inability to read upstream does not itself transfer authority elsewhere.

### 5.2 Remote Location

**Question answered:** Where should deterministic remote Project Source discovery start?

For a Git-backed Project, typical representation is:

```yaml
remote_location:
  repository: "OWNER/REPOSITORY"
  url: "https://github.com/OWNER/REPOSITORY"
```

Rules:

1. Remote Location is the deterministic remote discovery starting point, replacing recency/ranking guesses.
2. It is not a branch authority.
3. It is not automatically Canonical Implementation Source.
4. It is not automatically the current worktree.
5. Once active `FRAMEWORK-001` is found, its governed repository/storage bindings are authoritative for initialized-Project routing.
6. A remote mismatch is surfaced; the Agent does not silently choose whichever remote is newer.

The design keeps the first implementation Git-repository-oriented because the current Framework distribution and self-hosting workflow are Git-based. Provider-neutral extension may be added later without changing the semantic definition.

### 5.3 MCP Location

**Question answered:** Which Project workspace/root is the declared MCP execution surface expected to target for Material Project work in this environment?

Typical representation:

```yaml
mcp_location:
  environment: "Tai-F3_MCP / Windows"
  path: "E:\\GitHub\\ProjectFramework"
  repository: "captainhuke-dev/ProjectFramework"
```

Rules:

1. MCP Location is environment-scoped bootstrap execution routing, not a new Root Governance authority family.
2. The path SHOULD identify the Project workspace/root or permitted Project worktree boundary used by the MCP execution surface.
3. Repository identity SHOULD be included or verified for Git-backed Material work when practical.
4. MCP `workspaceId`, recent workspace, editor handle, or tool ranking remains routing evidence only.
5. A different active MCP workspace does not silently transfer Project authority.
6. Material work in a Git worktree associated with the declared repository may occur after current worktree/repository verification; creating or using the worktree does not persistently rewrite MCP Location merely because the concrete checkout path is a child/sibling worktree.
7. MCP Location does not grant `AUTH-*`, `DEL-*`, risk approval, branch integration, or runtime authority.

### 5.4 Local Workspace

**Question answered:** Where is the Project's local durable workspace/root in this execution environment?

Typical representation:

```yaml
local_workspace:
  environment: "Windows"
  path: "E:\\GitHub\\ProjectFramework"
```

Rules:

1. Local Workspace resolves the local Project root before local inspection or mutation.
2. It is environment-scoped; Windows/WSL/VM/remote workspaces may use different paths.
3. It is compatible with Framework `1.2.5` Local Workspace Binding and does not replace it.
4. Once active `FRAMEWORK-001` exists, the applicable governed Local Workspace Binding is authoritative.
5. Same folder name is insufficient when repository identity materially matters.
6. Local Workspace may equal MCP Location in a simple environment while retaining a different meaning.

### 5.5 current branch/worktree

**Question answered:** What Git execution state is active now?

Recommended bootstrap declaration is intentionally state-oriented rather than value-oriented:

```yaml
current_branch_worktree:
  state: "DYNAMIC"
  rule: "VERIFY_EACH_SESSION"
```

Rules:

1. Do not persist a branch name or worktree path as static bootstrap authority.
2. Resolve at least repository root/common-dir, current branch or detached state, HEAD, worktree path, and working-tree status when material to the task.
3. Worktree state does not redefine Remote Location, MCP Location, Local Workspace, Canonical Integration Target, or Canonical Implementation Source.
4. Branch/worktree observations in handoffs are continuation evidence and must be freshness-checked.
5. Framework `1.2.2` remains authoritative for Canonical Integration Target and Base Freshness.

### 5.6 File Storage Location

**Question answered:** Where are durable non-repository Project files/objects stored?

File Storage Location is zero-or-more because many Projects use multiple storage systems for different artifact classes. Each applicable storage entry reuses the existing Framework routing-state vocabulary exactly:

```text
BOUND
NOT_APPLICABLE
VERIFICATION_REQUIRED
```

Storage does **not** introduce a provider-specific or storage-specific state family. Each entry also records epistemic verification separately as `VERIFIED | USER_CONFIRMED | VERIFICATION_REQUIRED`.

Recommended bootstrap representation:

```yaml
file_storage_locations:
  - name: "project-documents"
    provider: "google_drive"
    binding_state: "BOUND"
    canonical_location: "<FOLDER_ID_OR_CANONICAL_URL>"
    purpose: "project documents and business artifacts"
    verification_status: "VERIFIED"

  - name: "datasets"
    provider: "s3"
    binding_state: "BOUND"
    canonical_location: "s3://bucket/prefix/"
    purpose: "datasets and large generated artifacts"
    verification_status: "USER_CONFIRMED"

  - name: "media-archive"
    provider: "nas"
    binding_state: "BOUND"
    canonical_location: "\\\\server\\share\\project"
    purpose: "large media/archive files"
    verification_status: "VERIFIED"
    local_mounts:
      Windows: "Y:\\project"
```

Rules:

1. File Storage Location is distinct from Remote Location and Local Workspace.
2. Storage provider may be Google Drive, S3/object storage, NAS/network share, durable filesystem, or another explicitly identified provider.
3. Each applicable storage entry MUST resolve independently as exactly `BOUND | NOT_APPLICABLE | VERIFICATION_REQUIRED`; implementation MUST NOT create a storage-specific state family.
4. `BOUND` requires sufficient durable provider identity for the declared artifact scope. Minimum identity is provider-specific: Google Drive folder ID/canonical URL; S3 bucket + applicable prefix or canonical `s3://` URI; NAS stable UNC/server-share identity when available; durable filesystem explicit canonical root/path for the applicable environment; another provider an equivalently stable locator.
5. `binding_state: BOUND` may use `verification_status: VERIFIED` when the provider/system identity was actually verified, or `USER_CONFIRMED` when the user supplied an unambiguous durable identity without claiming provider-level verification. A `BOUND` entry MUST NOT use `verification_status: VERIFICATION_REQUIRED`.
6. `VERIFICATION_REQUIRED` means the storage scope is known/applicable but no unambiguous durable target identity has yet been verified or user-confirmed sufficiently for Material routing. Read/search/discovery and user confirmation may resolve it; Material mutation through that unresolved scope is blocked by default.
7. `NOT_APPLICABLE` is an explicit state for a declared provider/scope that is outside the Project working-location contract. A Project with no external/non-repository storage may omit `file_storage_locations` entirely; it MUST NOT create synthetic `NOT_APPLICABLE` entries merely to populate a template.
8. Absence of a File Storage entry does not authorize inference or fallback. If a requested Material action requires external storage but no applicable declared entry can be resolved, the affected routing is treated as `VERIFICATION_REQUIRED` until Project scope and durable identity are resolved.
9. Each applicable location SHOULD declare its purpose/scope so the Agent can route by artifact ownership instead of recency.
10. A drive letter or local mount is environment-scoped access routing, not necessarily canonical storage identity.
11. File Storage Location does not automatically become Canonical Implementation Source, Runtime Persistent-State Boundary, or backup policy.
12. If a storage target is contradictory or mismatched, the affected storage mutation is fail-closed; the Agent MUST NOT fall back to another recent bucket/folder/share.
13. For Google Drive scope already governed by active `FRAMEWORK-001`, a bootstrap File Storage entry is discovery/routing input only; overlapping storage representation MUST NOT become a second conflicting Root Governance authority.

## 6. Recommended Bootstrap Location Block

The Project instruction layer should support a concise block equivalent to:

```yaml
framework_source:
  repository: "<FRAMEWORK_OWNER/REPO>"
  url: "<FRAMEWORK_URL>"
  bootstrap_ref: "main"

remote_location:
  repository: "<PROJECT_OWNER/REPO>"
  url: "<PROJECT_REPOSITORY_URL>"

mcp_location:
  environment: "<MCP_SURFACE / OS_OR_CONTEXT>"
  path: "<PROJECT_WORKSPACE_ROOT>"
  repository: "<PROJECT_OWNER/REPO_WHEN_GIT_BACKED>"

local_workspace:
  environment: "<LOCAL_ENVIRONMENT>"
  path: "<ABSOLUTE_PROJECT_ROOT>"

file_storage_locations:
  - name: "<STORAGE_SCOPE_NAME>"
    provider: "<google_drive | s3 | nas | filesystem | other>"
    binding_state: "<BOUND | NOT_APPLICABLE | VERIFICATION_REQUIRED>"
    canonical_location: "<DURABLE_PROVIDER_LOCATOR_OR_UNKNOWN_OR_NOT_APPLICABLE>"
    purpose: "<OWNED_ARTIFACT_SCOPE>"
    verification_status: "<VERIFIED | USER_CONFIRMED | VERIFICATION_REQUIRED>"
    local_mounts:
      <ENVIRONMENT>: "<OPTIONAL_LOCAL_MOUNT>"

current_branch_worktree:
  state: "DYNAMIC"
  rule: "VERIFY_EACH_SESSION"
```

Optional fields/providers may be omitted only when not applicable; unknown Material routing must not be fabricated.

## 7. Resolution and Precedence Contract

The deterministic order is:

```text
1. Read Bootstrap Location Block before Project Source discovery.
2. Use Framework Source only for Framework bootstrap/read-through.
3. Use Remote Location as the deterministic remote Project Source discovery start.
4. Use Local Workspace to resolve the local Project root.
5. Use MCP Location to resolve/verify the intended MCP execution boundary for this environment.
6. Use File Storage Location(s) to route non-repository artifacts by declared purpose/provider.
7. Verify current branch/worktree from Git whenever Git execution state matters.
8. If active local FRAMEWORK-001 is found, its governed Project Location state becomes authoritative over bootstrap Project-location hints.
9. Preserve Canonical Integration Target, Canonical Implementation Source, Runtime Location, Authority/Risk, and approval gates independently.
```

### 7.1 Mismatch handling

If bootstrap state and active `FRAMEWORK-001` materially conflict:

```text
stop affected Material mutation
→ report exact mismatch
→ do not silently rewrite Bootstrap Location Block
→ do not silently rewrite FRAMEWORK-001
→ use governed change path if the Project location genuinely changed
```

Active Root Governance wins as authority; the bootstrap mismatch remains evidence that the instruction/bootstrap configuration may need an explicitly approved update.

### 7.2 Persistent location changes

A persistent Project location change is not a side effect of discovery.

It requires:

1. explicit user approval for the persistent change;
2. governed `FRAMEWORK-001` revision/validation/promotion when initialized Project governance changes;
3. propagation to bootstrap instructions/configuration when necessary so future discovery remains deterministic;
4. no silent mutation of either side.

A one-off exact target instruction remains action-specific under Framework `1.2.4`/`1.2.5` semantics.

## 8. Required Semantic Separation

The Framework must state the separation explicitly:

```text
Framework Source
≠ Remote Location
≠ MCP Location
≠ Local Workspace
≠ File Storage Location
≠ current branch/worktree
≠ Project Location Binding authority
≠ Canonical Integration Target
≠ Canonical Implementation Source
≠ Runtime Location
```

Additional clarifications:

```text
Framework Source answers: where does Framework upstream live?
Remote Location answers: where do I start remote Project Source discovery?
MCP Location answers: where is this MCP execution surface expected to operate for this Project?
Local Workspace answers: where is the Project local workspace/root in this environment?
File Storage Location answers: where do durable non-repo files/objects for a declared scope live?
current branch/worktree answers: what Git execution state is active right now?
```

## 10. File Storage Topology Rules

### 10.1 Split code and artifact ownership

The following is first-class and expected:

```text
Remote Location / Local Workspace
  → Git repository owns code, config, Project Source

File Storage Location: Google Drive
  → business documents / office artifacts

File Storage Location: S3
  → datasets / large generated objects

File Storage Location: NAS
  → media / archive / exports
```

The Agent routes each Material write to the declared authoritative owner for that artifact scope.

### 10.2 Multiple storage locations

Multiple File Storage Locations MUST be purpose-scoped or otherwise disambiguated. Search ranking, connector recency, or easiest write access must not choose the owner.

### 10.3 Environment-specific mounts

A canonical remote/storage location may have different access paths:

```text
NAS canonical identity: \\storage01\projects\alpha
Windows workstation A: Y:\alpha
Windows workstation B: Z:\alpha
Linux: /mnt/projects/alpha
```

Those mount paths are environment-scoped routing evidence. They do not create three different storage authorities.

### 10.4 Storage vs implementation/runtime truth

File Storage Location may contain source inputs, generated artifacts, or persistent application data, but the label alone does not decide truth-domain authority.

If a Project needs a storage location to be Canonical Implementation Source or part of Runtime Persistent-State Boundary, the existing applicable Framework contracts must explicitly say so.

## 11. GREENFIELD, Initialized Projects, and Self-Hosting

### 11.1 GREENFIELD

When no active `FRAMEWORK-001` exists:

```text
Bootstrap Location Block
→ Framework Source read-through
→ deterministic Remote / Local / MCP / File Storage discovery as applicable
→ read-only verification of candidate identities
→ Preview proposed Project Location Binding / local/storage state
→ explicit approval
→ create active 00 / FRAMEWORK-001
→ governed steady-state routing
```

Unknown Material locations remain unresolved; no path/provider identity is guessed.

### 11.2 Existing initialized Projects

Existing Projects remain locally pinned and do not auto-upgrade.

Migration to `1.2.6` MUST NOT invent:

- repository URLs/owners;
- local absolute paths;
- MCP workspace IDs;
- environment labels;
- storage bucket/folder/share identities;
- local storage mounts;
- current branch/worktree;
- Canonical Integration Target;
- Canonical Implementation Source;
- runtime paths.

Projects that use only Git/local workspace and no external file storage remain valid without synthetic storage entries. Migration MUST NOT interpret an absent optional storage provider as `VERIFICATION_REQUIRED` merely because the 1.2.6 model supports it. If an external storage scope is explicitly known to be applicable but its durable identity is unresolved, that applicable scope is `VERIFICATION_REQUIRED`; if no external storage scope exists, the storage list may remain absent.

### 11.3 ProjectFramework self-hosting

ProjectFramework may legitimately have:

```text
Framework Source = captainhuke-dev/ProjectFramework
Remote Location = captainhuke-dev/ProjectFramework
MCP Location = E:\GitHub\ProjectFramework
Local Workspace = E:\GitHub\ProjectFramework
```

These equal values are a self-hosting coincidence. The terms remain distinct and current branch/worktree remains separately observed.

## 13. Pressure / Acceptance Scenarios

Framework `1.2.6` design requires pressure coverage for at least:

1. No active `FRAMEWORK-001`; multiple recent repos exist → use Remote Location as deterministic discovery start rather than recency.
2. Framework Source differs from Project repo → never mutate Framework upstream as if it were the Project.
3. ProjectFramework self-hosting makes Framework Source and Remote Location equal → meanings remain distinct.
4. Remote Location points to correct repository but prompt contains a stale branch → verify current branch/worktree and preserve Canonical Integration Target separation.
5. MCP active/recent workspace is another Project → configured/verified MCP Location and Local Workspace prevent mutation of the other Project.
6. MCP workspace ID changes while canonical path/repository remain correct → no persistent location rewrite.
7. MCP Location and Local Workspace use the same path → concepts remain distinct.
8. Active Material Git work occurs in an owned worktree under/associated with the declared Project repository → verify Git worktree/repository state; do not rewrite Local Workspace merely because checkout path differs.
9. Active `FRAMEWORK-001` repository/local binding conflicts with bootstrap block → active Root Governance wins; stop affected mutation and surface mismatch.
10. Git owns code while Google Drive owns business documents → route independently; no forced single location.
11. Git owns code while S3 owns datasets/artifacts → S3 is not automatically Canonical Implementation Source.
12. NAS canonical share has different drive-letter mounts on two machines → preserve canonical storage identity and environment-specific access paths.
13. Multiple storage providers exist → route by declared purpose/scope, not connector recency.
14. Known-applicable storage scope has unresolved durable identity → classify that affected storage routing as `VERIFICATION_REQUIRED`, fail closed for Material mutation, and do not fall back to another recent folder/bucket/share.
15. One-off exact storage/local target instruction → action-specific only; no persistent bootstrap or `FRAMEWORK-001` rewrite.
16. Existing Framework `1.2.5` Project uses GitHub/Drive/Local Workspace Binding but no generic storage list → upgrade does not invent S3/NAS, does not infer provider applicability from accessible resources, and does not force migration.
17. Repo-only Project has no external file storage → omit storage list; no synthetic `NOT_APPLICABLE` entries required. A future Material request that actually requires external storage is unresolved/`VERIFICATION_REQUIRED` until scope and identity are governed.
18. Framework Source is unreachable but valid initialized local Project Source exists → local pin remains authoritative; no automatic remote substitution.
19. Persistent location genuinely changed → requires explicit approval and governed propagation; discovery alone cannot rewrite it.
20. current branch/worktree differs from a stale handoff/bootstrap expectation → observed Git state is reported and stale expectation is not treated as authority.

This design branch materializes these as Scenarios `87–106` before `GREEN Run Instructions`; implementation must preserve and satisfy them.

## 14. Verification Strategy for the 1.2.6 Implementation

Implementation verification should be progressive and risk-scoped under Framework `1.2.5`:

### Task-level checks

- direct semantic token/structure checks for changed governance surfaces;
- launcher parity/size checks only when launchers change;
- pressure-scenario numbering/uniqueness checks when scenarios change;
- template/starter parity checks for affected location semantics;
- no accidental schema/Stable-ID changes.

### Release-candidate checks

A completed `1.2.6` candidate receives one full current-distribution verification bound to the candidate state, including applicable:

- release identity/version consistency;
- launcher parity and size;
- maintained starter/current-template alignment;
- Core/SKILL/root semantic invariants;
- pressure scenarios;
- Base Freshness and integration checks.

## 15. Success Criteria

Framework `1.2.6` design is satisfied when implementation can demonstrate all of the following:

1. A fresh Agent can determine where to start without guessing from recent activity.
2. Framework Source and Project source discovery are distinct.
3. Remote Location does not become branch or implementation authority.
4. MCP Location is deterministic for the execution surface without turning MCP IDs into canonical identity.
5. Local Workspace remains compatible with environment-scoped Local Workspace Binding.
6. current branch/worktree is always dynamic/observed.
7. Git code and Drive/S3/NAS/file storage can coexist as independent Project locations.
8. Each applicable File Storage Location reuses exactly `BOUND | NOT_APPLICABLE | VERIFICATION_REQUIRED`, separates verification status, and introduces no storage-specific state family.
9. Storage routing uses durable provider identity and declared purpose when material; known-applicable unresolved storage is `VERIFICATION_REQUIRED`, while Projects with no external storage need no synthetic entries.
10. Active `FRAMEWORK-001` remains canonical initialized-Project location authority.
11. Bootstrap/Root Governance mismatch is fail-closed for affected Material mutation and never silently rewrites either side.
12. Existing `1.2.5` Projects remain valid and do not receive invented location values or inferred provider applicability.
13. Canonical Integration Target, Canonical Implementation Source, Runtime Location, Authority, Risk, and approval remain independent.
14. Pressure scenarios `87–106` cover the accepted design cases.
15. Project Source Schema remains `1.0.0`.
