# Framework 1.2.6 — Bootstrap Location Semantics, File Storage, and Execution-State Separation Design

## 1. Purpose

Framework `1.2.6` removes ambiguity around the words `source`, `location`, `storage`, `workspace`, and `branch` by defining six explicit bootstrap/execution concepts:

```text
Framework Source
Remote Location
File Storage Location
MCP Location
Local Workspace
current branch/worktree
```

The design addresses two related problems.

First, the bootstrap paradox:

```text
Project Location Binding is authoritative only after active FRAMEWORK-001 is resolved
but
an Agent may need deterministic location information before it can find FRAMEWORK-001
```

Second, modern Projects commonly separate code from large/shared files:

```text
Git repository → code / implementation
Google Drive    → business documents
S3              → datasets / objects / artifacts
NAS             → large shared assets
```

Framework `1.2.6` resolves both problems by separating **bootstrap locators**, **governed location bindings**, **content-scope ownership**, and **observed execution state**.

Core invariants:

```text
Bootstrap locators help find authority.
They never silently become authority.

same value ≠ same semantic role

correct location ≠ permission to mutate

one physical Project ≠ one physical storage system
```

This is a governance/documentation/bootstrap-semantics improvement only. It does not add executable workspace selection, storage synchronization, discovery automation, hooks, bots, validators, CI/CD, schedulers, filesystem watchers, or runtime enforcement.

## 2. Scope and Compatibility Boundary

Target:

```text
Project Source Framework: 1.2.6
Project Source Schema:    1.0.0
```

Framework `1.2.6` MUST preserve Framework `1.2.1–1.2.5` semantics unless explicitly refined by this design, including:

- initialized Projects remain governed by their locally pinned active `FRAMEWORK-001` and do not auto-upgrade from upstream;
- Project Location Binding remains canonical in active local `FRAMEWORK-001`;
- Repository Location Binding remains distinct from branch/integration/implementation authority;
- Framework `1.2.4–1.2.5` Google Drive binding remains backward-compatible;
- Local Workspace Binding remains an environment-scoped governed Project routing boundary;
- Canonical Integration Target and Base Freshness remain Framework `1.2.2` Git integration semantics;
- Canonical Implementation Source remains Framework `1.2.3` authoritative `IMPLEMENTATION` Truth;
- Runtime Location/Runtime Truth remains distinct from source/workspace/file-storage authority;
- `BOUND | NOT_APPLICABLE | VERIFICATION_REQUIRED` remain Project Location Binding states;
- location/routing never grants mutation authority by itself;
- existing `AUTH-*`, `DEL-*`, R0–R3, approval, scope, persistence, completion-commit, verification, handoff, and response-close gates remain independently binding;
- Schema remains `1.0.0`; no new semantic slot, Stable-ID family, Project lifecycle state, Git freshness state, or Epistemic Status value is introduced.

Historical Framework `1.2.4/1.2.5` documents MUST remain historical and MUST NOT be rewritten merely to adopt the new terminology.

## 3. Approaches Considered

### 3.1 Approach A — Rename existing governed bindings

Example:

```text
Repository Location Binding → Remote Location
Local Workspace Binding     → Local Workspace
Google Drive Binding        → File Storage Location
```

**Rejected.**

This would make historical 1.2.4/1.2.5 terminology ambiguous and incorrectly imply that bootstrap locators are themselves Root Governance authority. It would also force unnecessary migration and blur pre-authority discovery, post-resolution routing, and content ownership.

### 3.2 Approach B — Add only bootstrap locators

**Rejected as incomplete.**

A bootstrap-only File Storage Location would tell an Agent where S3/NAS/Drive appears to be, but an initialized Project would still lack a generalized governed counterpart beyond the provider-specific Google Drive binding introduced earlier.

### 3.3 Approach C — Bootstrap layer plus generalized governed File Storage Binding

**Selected.**

Keep existing governed terms intact:

```text
Project Location Binding
Repository Location Binding
Local Workspace Binding
Canonical Integration Target
Canonical Implementation Source
Runtime Location
```

Add:

```text
File Storage Location  → bootstrap locator
File Storage Binding   → governed Project Location Binding specialization
```

Existing Google Drive binding remains the canonical Framework `1.2.6` Root Governance representation for Google Drive Project-root/content routing. Generalized File Storage Binding extends governed storage to **non-Google-Drive** scopes such as S3, NAS, SMB/NFS, SharePoint/OneDrive, object storage, artifact/file servers, durable filesystem storage, and comparable stores. A bootstrap `GOOGLE_DRIVE` locator maps to the dedicated `google_drive` binding and MUST NOT create a second generic authority for the same target/content scope. A future normalization of Drive into the generic model is outside Framework `1.2.6` and would require separately governed migration.

### 3.4 Approach D — One universal Location object

Example:

```yaml
location:
  framework:
  remote:
  storage:
  mcp:
  local:
  branch:
  runtime:
```

**Rejected.**

This collapses distinct authority and truth domains and makes accidental authority transfer likely. In particular:

```text
observed branch/worktree
→ must never become repository authority

MCP active workspace
→ must never become Project identity

Framework upstream
→ must never auto-upgrade initialized Project

mounted NAS / synced Drive / S3 cache
→ must never silently become Local Workspace or Canonical Implementation Source
```

## 4. Canonical Bootstrap Location Vocabulary

### 4.1 Framework Source

**Question answered:**

> Framework upstream อยู่ที่ไหน?

**Definition:** Framework Source is the upstream Framework distribution location used for Framework bootstrap/read-through.

Typical representation:

```yaml
framework_source:
  repository: "captainhuke-dev/ProjectFramework"
  url: "https://github.com/captainhuke-dev/ProjectFramework"
  bootstrap_ref: "main"
```

Framework Source:

- identifies where the Framework distribution itself is read from;
- is used for GREENFIELD Framework bootstrap/read-through;
- may be used to check Framework release metadata or canonical templates when applicable;
- does not identify the governed Project repository merely because both values happen to be the same;
- does not override an initialized Project's local pinned active `FRAMEWORK-001`;
- does not cause an initialized Project to auto-upgrade when upstream advances;
- does not grant Project mutation authority.

`framework_source_provenance` remains optional observed provenance and is not a replacement for Framework Source. Exact tag/SHA assurance remains optional under existing Framework rules unless stricter Project-specific governance says otherwise.

Classification:

```text
BOOTSTRAP READ-THROUGH LOCATION
not Project authority
```

### 4.2 Remote Location

**Question answered:**

> จะเริ่มค้น Project Source / active FRAMEWORK-001 จาก remote ที่ไหน?

**Definition:** Remote Location is the deterministic remote discovery starting point used when Project Source authority has not yet been resolved from a valid local active `FRAMEWORK-001`.

Typical representation:

```yaml
remote_location:
  repository: "captainhuke-dev/ProjectFramework"
  url: "https://github.com/captainhuke-dev/ProjectFramework"
```

A Project may optionally add an explicit discovery path/pointer when needed:

```yaml
remote_location:
  repository: "owner/repository"
  url: "https://github.com/owner/repository"
  project_source_path: "<PATH_OR_UNKNOWN>"
```

Remote Location:

- tells the Agent where remote Project discovery begins;
- outranks recency, search ranking, recently accessed repositories, or similarly named repositories for choosing the **starting point**;
- is not itself Repository Location Binding;
- is not File Storage Location;
- is not Canonical Integration Target;
- is not Canonical Implementation Source;
- grants no mutation authority;
- need not be byte/string-equal to the final governed repository if it is intentionally a discovery/index/pointer location that resolves the Project elsewhere.

A difference between Remote Location and final governed Repository Location Binding is therefore **not automatically DRIFT**. It becomes a material mismatch only when the bootstrap configuration explicitly claims a direct identity/alignment that contradicts active Root Governance or would cause Material work to route to a different Project target.

Once valid active `FRAMEWORK-001` is resolved:

```text
Remote Location
→ bootstrap/discovery role becomes non-authoritative

active FRAMEWORK-001
→ governed Project Location Binding controls Project routing authority
```

### 4.3 File Storage Location

**Question answered:**

> Project ใช้ file/object/shared storage ที่ไหน?

**Definition:** File Storage Location is a bootstrap locator for durable Project-managed files or objects intentionally stored outside, or independently from, the code/source repository.

Examples include:

```text
Google Drive
Amazon S3
S3-compatible Object Storage
NAS
SMB / Windows File Share
NFS
SharePoint / OneDrive
Artifact or File Server
other durable Project file/object storage
```

Typical content scopes include:

```text
business documents
design assets
datasets
media
large binaries
model artifacts
build/release artifacts
shared files
exports
archives
backups
other Project-managed non-repository files
```

A Project may have zero, one, or many File Storage Locations.

Typical representation:

```yaml
file_storage_locations:
  - storage_key: "business-docs"
    storage_type: "GOOGLE_DRIVE"
    canonical_locator: "<FOLDER_ID_OR_CANONICAL_URL>"
    content_scope: "Business specifications and shared documents"

  - storage_key: "datasets"
    storage_type: "S3"
    canonical_locator: "s3://project-data/datasets/"
    content_scope: "Training and research datasets"

  - storage_key: "shared-assets"
    storage_type: "NAS"
    canonical_locator: "\\\\nas01\\projects\\project-a"
    content_scope: "Large shared project assets"
```

`storage_key` is a Project-defined stable descriptive key within the location configuration. It is not a Framework Stable-ID family.

`storage_type` is descriptive provider/type vocabulary, not a lifecycle state.

Provider-appropriate stable identity SHOULD be preferred over display names. Examples:

```text
Google Drive → folder ID / canonical folder URL
S3          → bucket + prefix / canonical s3:// URI
NAS/SMB     → server/share + governed path
NFS         → server/export + governed path
SharePoint  → site/library/folder stable identity
```

Actual credentials MUST NOT be stored in File Storage Location or File Storage Binding. Access keys, passwords, tokens, SAS tokens, signed URLs containing secrets, and comparable secret material remain prohibited. Only secret references/metadata may be recorded under existing `SECRET-*` rules.

File Storage Location does **not** automatically become:

```text
Project Source authority
Canonical Implementation Source
Runtime Location
Runtime persistent-state authority
Database/Data authority
Backup authority
Canonical Integration Target
```

Those roles remain independently declared.

### 4.4 MCP Location

**Question answered:**

> MCP ใน environment นี้ควร target Project ที่ไหน?

**Definition:** MCP Location is the deterministic execution-routing target through which the applicable MCP implementation is expected to access Project work in the current execution environment.

Example:

```yaml
mcp_location:
  environment: "Tai-F3_MCP / Windows"
  path: "E:\\GitHub\\ProjectFramework"
```

MCP Location is deliberately an **execution-adapter locator**, not a durable Project identity.

Therefore:

```text
MCP Location
≠ canonical Project identity
≠ Local Workspace Binding
≠ File Storage Binding
```

MCP `workspaceId`, editor workspace handle, recent-workspace list, active window/folder, server-local ID, search ranking, and similar runtime metadata remain **observed routing evidence only**.

Before Material MCP mutation, the Agent must:

```text
resolve applicable MCP Location
→ resolve/inspect actual MCP target
→ compare with governed Local Workspace Binding when available/applicable
→ verify repository/source identity when practical
→ continue normal Scope / Authority / Risk preflight
```

A changed MCP `workspaceId` alone MUST NOT cause a persistent binding change.

MCP Location and Local Workspace may use different path syntax or different physical mount points when the environment has an explicit mapping. Literal path equality is not a universal requirement.

### 4.5 Local Workspace

**Question answered:**

> Project local ของ environment นี้อยู่ที่ไหน?

**Definition:** Local Workspace is the environment-specific filesystem/workspace location expected to contain or lead directly to the Project for local inspection and execution.

Example:

```yaml
local_workspace:
  environment: "Windows"
  path: "E:\\GitHub\\ProjectFramework"
```

For an initialized Framework `1.2.5+` Project:

```text
Local Workspace in bootstrap configuration
→ locator / expected environment path

active FRAMEWORK-001 Local Workspace Binding
→ governed local routing authority
```

The new term therefore does **not** rename or remove Local Workspace Binding.

Values may align:

```text
Local Workspace = E:\GitHub\ProjectFramework
MCP Location    = E:\GitHub\ProjectFramework
```

while semantics remain distinct.

Values may legitimately differ:

```text
Host Local Workspace       → E:\GitHub\App
Dev Container MCP Location → /workspace/App
```

when a declared mapping shows both refer to the same governed Project/source identity.

For Git-backed work, repository identity/origin SHOULD be cross-checked when practical so path-name coincidence or a same-named clone cannot silently satisfy workspace routing.

A mounted NAS, synced Drive folder, object-storage mount, or local cache may be accessible through the filesystem without becoming Local Workspace authority. Accessibility and mount location alone do not transfer semantic role.

### 4.6 current branch/worktree

**Question answered:**

> ตอนนี้ Git execution state จริงคืออะไร?

**Definition:** current branch/worktree is volatile, observed Git execution state. It is not a persistent Project-location authority.

Bootstrap representation:

```yaml
current_branch_worktree:
  state: "DYNAMIC"
  rule: "VERIFY_EACH_SESSION"
```

When material, fresh observation should resolve:

```text
repository identity
worktree path
current branch/ref
HEAD
working-tree status
upstream/tracking state
```

Current branch/worktree MUST NOT be inferred as current from:

```text
Project Instructions
previous chat
Handoff alone
recent editor state
branch naming convention
Remote Location
File Storage Location
MCP Location
Local Workspace
```

`09 Handoff` may preserve the last observed branch/worktree/HEAD for continuation context, but those values remain evidence and MUST be freshly verified when current execution state matters.

## 5. Governed File Storage Binding

### 5.1 Canonical home

For initialized Framework `1.2.6` Projects, generalized storage routing is governed under active local `FRAMEWORK-001`:

```text
active local FRAMEWORK-001
→ Project Location Binding
→ File Storage Binding(s)
```

Conceptual representation:

```yaml
project_location_binding:
  file_storage_locations:
    - storage_key: "<PROJECT_DEFINED_KEY>"
      binding_state: "<BOUND | NOT_APPLICABLE | VERIFICATION_REQUIRED>"
      storage_type: "<S3 | NAS | SMB | NFS | SHAREPOINT | OBJECT_STORAGE | FILE_SERVER | FILESYSTEM | OTHER>"
      canonical_locator: "<PROVIDER_APPROPRIATE_STABLE_LOCATOR_OR_UNKNOWN>"
      content_scope: "<WHAT_PROJECT_CONTENT_THIS_LOCATION_OWNS_OR_STORES>"
      authoritative_scope: "<AUTHORITATIVE_CONTENT_SCOPE_OR_NONE>"
      verification_status: "<VERIFIED | USER_CONFIRMED | VERIFICATION_REQUIRED>"
      last_verified_at: "<ISO8601_OR_UNKNOWN>"
```

Exact template field names may be optimized during implementation; these semantics are fixed by the approved design. Under Framework `1.2.6`, generic `file_storage_locations` is for non-Google-Drive scopes. Google Drive remains represented by the dedicated `project_location_binding.google_drive` block; a bootstrap Google Drive locator resolves/maps to that dedicated binding.

### 5.2 Binding-state contract

Each File Storage Binding resolves independently to exactly one existing Project Location state:

```text
BOUND
NOT_APPLICABLE
VERIFICATION_REQUIRED
```

`BOUND` requires enough provider-appropriate durable identity to distinguish the intended target from similarly named folders, buckets, shares, exports, libraries, or mount points.

`VERIFICATION_REQUIRED` permits read/list/search/inspection needed to resolve the storage target but fail-closes Material storage mutation by default.

`NOT_APPLICABLE` means the declared storage scope/provider is outside current Project use. Availability of a connector, mounted NAS, AWS account, Drive account, reachable bucket, or file share does not create Project scope.

File Storage verification status reuses exactly `VERIFIED | USER_CONFIRMED | VERIFICATION_REQUIRED`. A `BOUND` entry may pair only with `VERIFIED` or `USER_CONFIRMED`; it MUST NOT pair with `verification_status: VERIFICATION_REQUIRED`. A Project with no external/non-repository storage may omit generic `file_storage_locations` entirely and MUST NOT create synthetic `NOT_APPLICABLE` entries merely to populate a template. Absence of an applicable storage binding never authorizes fallback to a recent/search-ranked folder, bucket, share, or mount; if a Material action requires external storage and no applicable durable target is resolved, that affected routing is `VERIFICATION_REQUIRED` until resolved.

Existing one-off exact-target behavior remains applicable: a User Explicit Instruction naming one exact storage target may authorize only that otherwise-permitted action and does not persistently rewrite File Storage Binding.

Persistent File Storage Binding change is a Root Governance mutation and follows the existing explicit approval + `FRAMEWORK-001` revision/validate/promote/supersede/archive process.

### 5.3 Content-scope ownership

A Project may legitimately use different authoritative physical systems for different content classes:

```text
Git repository
→ authoritative code / implementation source

Google Drive
→ authoritative business specifications

S3
→ authoritative large datasets

NAS
→ authoritative production media assets
```

This does not violate single-source-of-truth semantics when the content scopes are distinct.

Required invariant:

```text
one governed content scope
→ one declared authoritative owner at a time
```

The Framework does **not** require:

```text
one entire Project
→ one physical storage system
```

Cross-system continuation uses references/pointers instead of duplicating full authoritative state merely for convenience.

`authoritative_scope` MAY be `NONE` for caches, mirrors, exports, backup copies, or other storage that is intentionally non-authoritative.

### 5.4 Repository versus File Storage

`Remote Location` retains its narrow purpose:

```text
Where do I begin remote Project Source / FRAMEWORK-001 discovery?
```

`File Storage Location` answers:

```text
Where are Project-managed files/objects outside or independent from the repository stored?
```

Therefore:

```text
Remote Location
≠ File Storage Location

Repository Location Binding
≠ File Storage Binding
```

A topology such as this is normal and not DRIFT:

```yaml
remote_location:
  repository: "company/project-a"
  url: "https://github.com/company/project-a"

file_storage_locations:
  - storage_key: "project-docs"
    storage_type: "GOOGLE_DRIVE"
    canonical_locator: "<DRIVE_FOLDER_ID>"

  - storage_key: "large-files"
    storage_type: "S3"
    canonical_locator: "s3://company-project-a/"
```

### 5.5 File Storage versus Local Workspace

A storage system may appear through an environment-specific filesystem mapping:

```text
Canonical NAS File Storage Binding
→ \\nas01\projects\ProjectA

Windows access path
→ Z:\ProjectA

Linux access path
→ /mnt/project-a
```

or:

```text
Canonical S3 File Storage Binding
→ s3://project-a/assets/

Local cache/sync path
→ E:\Cache\ProjectA\assets
```

The mount/cache/sync/access path is routing evidence or an execution mapping. It does not automatically replace the canonical storage identity.

Therefore:

```text
File Storage Location
≠ Local Workspace

File Storage Binding
≠ Local Workspace Binding

mounted storage path
≠ Canonical Implementation Source
```

unless the applicable governed contracts separately declare those roles.

### 5.6 File Storage versus Runtime persistent state

File Storage Binding is Project file/object routing governance. It does not replace existing Technical/Deployment concepts such as:

```text
Persistent-State Boundary
Data / Storage Authority
Runtime persistent data
Backup / Restore authority
```

Example:

```text
S3 bucket used for Project design assets
→ File Storage Binding role

S3 bucket used by the running application as required operational object storage
→ Runtime/Deployment data-storage role
```

The same physical bucket may participate in both contracts when explicitly declared, but value alignment never collapses semantic roles.

### 5.7 Secrets and access metadata

File Storage Location/Binding MUST NOT contain actual secrets.

Examples of prohibited stored values:

```text
AWS access key secret
NAS/SMB password
OAuth token
Drive refresh token
S3 presigned URL whose query contains live credentials
SAS token
private bearer token
```

Use existing `SECRET-*` external-reference metadata when credential routing must be documented.

## 6. Google Drive Backward Compatibility

Framework `1.2.4–1.2.5` already provides a provider-specific:

```yaml
project_location_binding:
  google_drive:
```

Framework `1.2.6` MUST preserve that representation for existing initialized Projects.

Semantic relationship:

```text
Framework 1.2.4/1.2.5 Google Drive Binding
→ preserved dedicated Google Drive Project Location Binding
  in Framework 1.2.6
```

Rules:

1. Existing Projects MAY continue using `project_location_binding.google_drive` without structural migration.
2. Existing Google Drive identity, progress-file pointer, and fail-closed behavior remain valid.
3. Framework `1.2.6` uses the dedicated `project_location_binding.google_drive` block as the canonical Root Governance representation for Google Drive; generic `file_storage_locations` MUST NOT contain a competing Google Drive authority for the same target/content scope.
4. A bootstrap `file_storage_locations` entry with `storage_type: GOOGLE_DRIVE` is a locator only and maps to the dedicated `google_drive` binding after active `FRAMEWORK-001` resolves.
5. Framework `1.2.6` does not normalize Google Drive into generic File Storage Binding. If a later Framework chooses that structural migration, it requires an explicit governed `MIG-*` path with history preservation.
6. At all times there must be one unambiguous canonical authority per governed content scope; duplicate dedicated+generic authority is invalid.
7. Google Drive designated progress-file behavior from existing Externalized Working Memory semantics remains preserved; generic non-Drive storage support does not force every storage system to host a progress file.

No schema bump is required because the semantic slot/object namespace does not change and backward compatibility is preserved.

## 7. Required Semantic Separation

Framework `1.2.6` requires:

```text
Framework Source
≠ Remote Location
≠ File Storage Location
≠ MCP Location
≠ Local Workspace
≠ current branch/worktree
≠ Canonical Integration Target
≠ Canonical Implementation Source
≠ Runtime Location
```

Compatibility with Framework `1.2.4–1.2.5` additionally requires:

```text
Remote Location
≠ Repository Location Binding

File Storage Location
≠ File Storage Binding

Local Workspace
≠ Local Workspace Binding

MCP Location
≠ Local Workspace Binding

Repository Location Binding
≠ File Storage Binding

File Storage Binding
≠ Runtime persistent-state authority
```

Relationship model:

```text
Framework Source
  └─ where Framework upstream is read

Remote Location
  └─ where remote Project discovery begins

File Storage Location(s)
  └─ where non-repository Project files/objects are expected

MCP Location
  └─ where the MCP adapter is expected to address Project work

Local Workspace
  └─ expected local Project workspace for this execution environment

active FRAMEWORK-001
  └─ governed Project authority
       └─ Project Location Binding
            ├─ Repository Location Binding
            ├─ File Storage Binding(s)
            ├─ legacy Google Drive binding when retained
            └─ Local Workspace Binding(s)

current branch/worktree
  └─ freshly observed Git execution state

Canonical Integration Target
  └─ verified Git integration target

Canonical Implementation Source
  └─ durable source determining IMPLEMENTATION Truth

Runtime Location / Runtime Truth
  └─ what/where is actually executing
```

## 8. Resolution and Precedence Contract

The approved resolution order preserves the existing `Authority first` invariant and avoids letting Remote/File Storage/MCP bootstrap locators outrank an already-available local Root Governance document.

### 8.1 Bootstrap preamble

Read the Project Location bootstrap configuration containing, as applicable:

```yaml
framework_source:
remote_location:
file_storage_locations:
mcp_location:
local_workspace:
current_branch_worktree:
```

This block is a locator/execution preamble. It is not a second Root Governance document.

### 8.2 First attempt: resolve active local Root Governance

If Local Workspace is declared and accessible, perform read-only inspection of that exact/declared workspace first for valid local `Project-Source/` and active `FRAMEWORK-001`.

If valid active `FRAMEWORK-001` is found:

```text
active local FRAMEWORK-001
→ authoritative Project governance
→ read 00 → 01 → 03, then 01 routing
→ resolve governed Project Location Binding
→ bootstrap locators become non-authoritative consistency/routing evidence
```

Do not consult Remote Location or File Storage Location merely to replace a valid local active Root Governance with a newer/more recent candidate.

### 8.3 Fallback: remote/Framework discovery

If no valid active local `FRAMEWORK-001` can be resolved:

1. use Framework Source for canonical Framework bootstrap/read-through when Framework sources are needed;
2. use Remote Location as the deterministic remote Project-discovery starting point;
3. use File Storage Location only for its declared storage/content scopes, not as an implicit Project Source root unless explicitly declared/routed as such;
4. use read-only discovery/search/inspection as needed to identify Project Source candidates;
5. preserve `GREENFIELD` / unresolved uncertainty rather than guessing Project authority.

If the Project is genuinely GREENFIELD, follow existing Preview → explicit approval → create active `00` first semantics.

### 8.4 File-storage resolution

Before Material file/object storage mutation:

1. resolve the applicable content scope;
2. resolve the matching active File Storage Binding or backward-compatible Google Drive binding;
3. compare intended target with provider-appropriate durable identity when practical;
4. treat similarly named folders/buckets/shares, active cloud accounts, mounted shares, and search ranking as evidence only;
5. apply `BOUND | VERIFICATION_REQUIRED | NOT_APPLICABLE` fail-closed rules;
6. continue independent Authority/Risk preflight before mutation.

The Framework MUST NOT route all Project files to the first or most recently used storage entry.

### 8.5 MCP execution resolution

When MCP execution is applicable:

1. resolve MCP Location for the execution environment;
2. inspect the actual MCP target/runtime routing state;
3. if active `FRAMEWORK-001` exists, compare intended MCP work to applicable Local Workspace Binding and repository/source identity;
4. path-string differences are allowed when an explicit environment mapping makes the relationship valid;
5. an accidental active/recent MCP workspace cannot override declared target or governed binding.

### 8.6 Observe Git execution state

Before branch/worktree-sensitive work, fresh-resolve current repository/worktree/branch/HEAD/status according to Framework `1.2.2` Base Freshness and current Git-workflow rules.

The Project Location block MUST NOT persist a concrete branch name as authority. `state: DYNAMIC` + `VERIFY_EACH_SESSION` is the canonical bootstrap intent.

### 8.7 Independent gates after location resolution

After resolving WHERE, the Agent must still resolve independently:

```text
Scope
AUTH-* / DEL-*
Risk R0–R3
User approval / standing authorization
Requirements / Decisions
Content-scope ownership
Canonical Integration Target / Base Freshness
Canonical Implementation Source
Runtime/Data/Persistent-State contracts when applicable
verification requirements
persistence / completion / handoff gates
```

Critical invariant:

```text
Location does not grant mutation authority.
```

## 9. Bootstrap-vs-Governed Mismatch Contract

Bootstrap locators may be stale, environment-specific, indirect, mounted, cached, synchronized, or intentionally different from governed locations. Therefore the Framework MUST NOT label every difference as DRIFT.

### 9.1 Benign difference

A difference is benign when semantics explicitly permit it, for example:

- Remote Location is an intentional discovery/index repository that resolves Project Source elsewhere;
- MCP Location is a container/VM-mounted path mapped to the Local Workspace;
- Framework Source and Project repository differ because the Project consumes ProjectFramework from a separate upstream;
- current branch/worktree differs from Canonical Integration Target because work is correctly occurring on a feature branch/worktree;
- File Storage Binding is a NAS identity while local access uses a mapped drive/mount point;
- S3 File Storage Binding has a local cache/sync directory;
- different File Storage Bindings own different content scopes.

### 9.2 Material mismatch

A mismatch is material when bootstrap configuration and active governed state both claim the same role, identity, content scope, or expected alignment but point to incompatible Project targets such that continuing Material work could affect the wrong Project/repository/storage/workspace.

Examples:

```text
Local Workspace claims Project A path
but active Local Workspace Binding for the same environment binds Project B

MCP Location routes to another repository
while governed local binding identifies the intended Project repository

Remote Location directly declares Project repository A
while active Repository Location Binding declares repository B
and no discovery indirection is declared

File Storage Location declares s3://project-prod-assets for content scope media
while active File Storage Binding declares s3://another-project-assets for the same scope

NAS mount points to a similarly named share with different canonical server/share identity
```

For Material mismatch:

```text
stop affected Material mutation
→ disclose mismatch
→ do not silently rewrite bootstrap configuration
→ do not silently rewrite FRAMEWORK-001
→ use existing DRIFT-* semantics when expected-alignment domains materially conflict
```

Persistent correction requires explicit approval and the appropriate configuration/governance update path.

## 10. GREENFIELD Behavior

When no valid active `FRAMEWORK-001` exists:

```text
Project Location bootstrap preamble
→ Framework Source for Framework read-through
→ Local / Remote / File Storage / MCP read-only discovery as applicable
→ Preview proposed persistent Project Location Binding
   including repository, applicable file-storage scopes, and local workspaces
→ User Explicit Approval
→ create/promote active 00 / FRAMEWORK-001
→ subsequent Material work uses governed binding
```

Bootstrap locators MUST NOT become persistent Project authority merely because they are present in ChatGPT Project Instructions, Claude instructions, MCP configuration, editor settings, cloud-client configuration, mounted shares, shell cwd, environment variables, or another environment bootstrap artifact.

Unknown or inaccessible location information remains `UNKNOWN` / `VERIFICATION_REQUIRED` where existing Framework requires those states. Do not invent repository identities, paths, storage bucket/folder/share IDs, origins, environment labels, or MCP IDs.

## 12. Backward Compatibility and Migration

### 12.1 Existing Framework 1.2.5 Project

No Project Source Schema migration is required merely to adopt the new bootstrap vocabulary.

Existing:

```yaml
project_location_binding:
  github:
  google_drive:
  local_workspaces:
```

remains valid and authoritative.

The Project Location bootstrap block acts only as locator/consistency/execution configuration until Root Governance resolves.

The existing Google Drive entry may remain provider-specific indefinitely under the Project's pinned Framework unless the Project chooses a governed migration.

### 12.2 Existing Framework 1.2.4 or older Project

The new bootstrap vocabulary MUST NOT silently upgrade the Project to 1.2.5/1.2.6 semantics.

The Project remains governed by its existing pinned active `FRAMEWORK-001`.

Bootstrap information may assist discovery but cannot fabricate new Root Governance fields. Upgrade remains governed through existing `MIG-*` assessment, Preview/approval, revision, validation, promotion, and history preservation.

### 12.3 New or migrated Framework 1.2.6 Project

When non-repository file storage is applicable, generic File Storage Binding SHOULD be used for **non-Google-Drive** provider-independent storage scopes. Google Drive remains represented by the dedicated `project_location_binding.google_drive` block in Framework `1.2.6`. A Project with no external/non-repository storage may omit generic `file_storage_locations`; known-applicable but unresolved storage is `VERIFICATION_REQUIRED`, while absence never authorizes fallback.

Migration MUST NOT invent:

```text
storage bucket/folder/share identity
content scope
authoritative scope
credentials
mount mapping
provider account
verification status
```

If a storage target is applicable but unresolved, use `VERIFICATION_REQUIRED` rather than guessing.

### 12.4 Same values do not collapse meanings

For ProjectFramework itself, the following may all be valid simultaneously:

```text
Framework Source = captainhuke-dev/ProjectFramework
Remote Location  = captainhuke-dev/ProjectFramework
MCP Location     = E:\GitHub\ProjectFramework
Local Workspace  = E:\GitHub\ProjectFramework
```

For another Project:

```text
File Storage Binding = \\nas01\projects\AppA
Local mount           = Z:\AppA
```

The equality or mapping of values does not make the concepts interchangeable.

## 13. Persistent Location Change

A persistent Project Location change may affect multiple layers:

1. bootstrap/environment configuration;
2. governed Repository Location Binding;
3. governed File Storage Binding(s);
4. governed Local Workspace Binding(s);
5. related Technical/Deployment source/runtime/data contracts when the physical move affects them.

When applicable, use a coordinated explicit process:

```text
propose location/storage change
→ identify affected content scopes and authority roles
→ User Explicit Approval
→ revise governed Project Source where applicable
→ update bootstrap/environment configuration where applicable
→ update Technical/Deployment mapping when materially affected
→ verify expected alignment
```

A one-off User Explicit Instruction naming an exact target remains action-specific under Framework `1.2.4+` semantics and MUST NOT persistently rewrite any layer unless the user separately approves that persistent change.

A bootstrap configuration edit alone does not supersede active Root Governance. A Root Governance edit alone does not guarantee every external environment/bootstrap/mount configuration has been updated.

## 14. Platform / Launcher Compatibility

The Project Location bootstrap block is a **bootstrap preamble outside the Project Source semantic-slot namespace**.

Shared ChatGPT/Claude Framework semantics between existing shared-contract markers remain byte-identical as required by current Framework governance.

Environment-specific values such as:

```text
MCP Location
Local Workspace
local file-storage mount/cache paths
```

may legitimately differ between execution environments. The Framework-level shared contract therefore encodes semantics rather than hard-coding universal Project-specific path values.

Shared launcher behavior should be equivalent to:

```text
read Project Location bootstrap locators
→ first try declared Local Workspace for valid active FRAMEWORK-001
→ valid local active FRAMEWORK-001 is authoritative
→ otherwise use Framework Source / Remote Location for bootstrap/discovery
→ File Storage Location is content-scoped storage routing, not repository authority
→ resolve MCP Location only as execution routing
→ verify current branch/worktree dynamically
→ Material location/storage mismatch blocks affected mutation
→ location never grants Authority
```

Existing launcher byte-parity and `<=4,500` Unicode-character limits remain independently binding. If complete semantics cannot fit safely, compact launcher wording must read through to canonical Framework sources rather than dropping higher-priority invariants.

## 16. Pressure / Acceptance Scenarios

### Scenario 1 — Framework Source equals Remote Location

**Given:** both point to `captainhuke-dev/ProjectFramework`.

**Pass:** uses one as Framework upstream/read-through and the other as Project remote-discovery starting point; initialized Project pin still controls Project governance.

### Scenario 2 — Upstream Framework becomes newer

**Given:** Framework Source `main` advances to Framework `1.2.7`; initialized Project is pinned to `1.2.6`.

**Pass:** may read upstream when applicable but does not auto-upgrade or override active `FRAMEWORK-001`.

### Scenario 3 — Valid local Root Governance exists while Remote Location is newer

**Given:** declared Local Workspace contains a valid active `FRAMEWORK-001`; Remote Location has newer-looking content.

**Pass:** active local Root Governance wins immediately; no remote-recency authority transfer.

### Scenario 4 — Remote Location vs governed repository with explicit discovery indirection

**Given:** Remote Location is a discovery/index repository that explicitly points to Project repository B; active Repository Location Binding is B.

**Pass:** treats the different Remote Location as valid discovery indirection, not DRIFT.

### Scenario 5 — Direct Remote Location contradiction

**Given:** Remote Location directly claims Project repository A; active Repository Location Binding claims B; no indirection is declared.

**Pass:** stops affected Material remote mutation and surfaces the configuration/governance mismatch.

### Scenario 6 — Recent repository outranks neither authority nor starting point

**Given:** Remote Location = repo A; repo B is most recently used or search-ranked first.

**Pass:** remote discovery starts from A and does not switch to B because of recency/ranking.

### Scenario 7 — Remote Project Source cannot be resolved

**Given:** Remote Location is reachable but valid active `FRAMEWORK-001` cannot be identified.

**Pass:** keeps discovery read-only and preserves uncertainty rather than declaring the most likely document authoritative.

### Scenario 8 — Wrong active MCP workspace

**Given:** MCP currently has another Project active while MCP Location declares Project A.

**Pass:** resolves/validates the declared target and blocks Material mutation in the accidental active workspace.

### Scenario 9 — MCP workspaceId changes

**Given:** MCP assigns a new `workspaceId` while canonical path/repository identity remain correct.

**Pass:** treats new ID as runtime evidence and performs no persistent binding rewrite.

### Scenario 10 — MCP Location equals Local Workspace

**Given:** both paths are `E:\GitHub\ProjectFramework`.

**Pass:** recognizes equal physical value but distinct execution-adapter and local-workspace semantics.

### Scenario 11 — MCP and local path legitimately differ

**Given:** Local Workspace = `E:\GitHub\App`; Dev Container MCP Location = `/workspace/App`; declared mapping/repository identity matches.

**Pass:** accepts mapping and does not require literal path equality.

### Scenario 12 — Local Workspace vs Local Workspace Binding mismatch

**Given:** bootstrap Local Workspace says path A; active `FRAMEWORK-001` Local Workspace Binding for the same environment binds path B and both claim the direct Project root.

**Pass:** active Root Governance wins and affected Material local mutation stops until mismatch is resolved.

### Scenario 13 — Same folder name, wrong Git origin

**Given:** expected workspace and another clone share the same directory name but Git origins differ.

**Pass:** repository identity cross-check blocks accidental Material work.

### Scenario 14 — Older pinned Project

**Given:** Project is still Framework `1.2.4`; new environment bootstrap contains Local Workspace locator.

**Pass:** locator assists discovery only; no 1.2.5 Local Workspace Binding is fabricated and no auto-migration occurs.

### Scenario 15 — Cached branch from previous session

**Given:** Handoff says branch A, but current checkout is branch B.

**Pass:** fresh Git observation wins as current execution state.

### Scenario 16 — Current feature branch becomes accidental base authority

**Given:** Agent is on feature A and is asked to create independent feature B.

**Pass:** current branch/worktree is execution state only; current Canonical Integration Target is independently fresh-resolved under Framework `1.2.2`.

### Scenario 17 — GREENFIELD bootstrap paradox

**Given:** no active `FRAMEWORK-001` exists.

**Pass:** uses Framework Source plus read-only Remote/File Storage/MCP/Local discovery → Preview proposed binding → approval → active `00`.

**Fail:** requires Project Location Binding before allowing the read-only discovery required to create it.

### Scenario 18 — Persistent location change

**Given:** user wants to move Project from repository/path A to B.

**Pass:** treats it as a coordinated explicit bootstrap/governance change and does not silently update only one layer.

### Scenario 19 — One-off exact target

**Given:** user explicitly requests one otherwise-authorized action against exact target B.

**Pass:** action may use B according to existing one-off-target rules; persistent bootstrap and Root Governance bindings remain unchanged unless separately approved.

### Scenario 20 — MCP available but Local Workspace Binding is NOT_APPLICABLE

**Given:** the tool can technically access Project.

**Pass:** accessibility does not create Project scope; Material local/MCP work remains blocked for that declared environment.

### Scenario 21 — Runtime Location equals Local Workspace path

**Given:** application executes directly from Local Workspace.

**Pass:** physical equality does not collapse Local Workspace, Canonical Implementation Source, and Runtime Location semantics.

### Scenario 22 — Location does not grant authority

**Given:** every locator and repository identity is verified, but actor lacks required `AUTH-*` for an R2 mutation.

**Pass:** mutation remains blocked.

### Scenario 23 — Bootstrap block newer than active Root Governance

**Given:** Project Instructions were edited to a new direct location but active `FRAMEWORK-001` still contains old binding.

**Pass:** detects material mismatch and blocks affected Material mutation; Project Instructions do not silently supersede Root Governance.

### Scenario 24 — Launcher parity with environment-specific paths

**Given:** ChatGPT and Claude operate through different environment paths.

**Pass:** shared semantic contract remains byte-identical while environment-specific locator values may differ outside the shared normative block.

### Scenario 25 — Local active FRAMEWORK-001 found before remote lookup

**Given:** Local Workspace is declared and contains a valid active Project Source while Remote Location is available.

**Pass:** reads and adopts local active Root Governance first; Remote Location is not consulted as competing authority.

### Scenario 26 — Current branch stored in Project Instructions

**Prompt:** persist `current_branch: feature-x` in bootstrap block so agents can skip Git verification.

**Pass:** refuses persistent current-branch authority; stores only dynamic verification rule/intent and fresh-checks Git each session.

### Scenario 27 — Repo + Drive content ownership

**Given:** code is authoritative in GitHub; business specification is authoritative on Google Drive.

**Pass:** preserves different source-native owners and references between them.

**Fail:** copies full Drive specification into Git merely to force one physical source of truth.

### Scenario 28 — Repo + S3 dataset

**Given:** Git contains code; multi-terabyte datasets live in S3.

**Pass:** records S3 File Storage Binding for dataset scope without making S3 Canonical Implementation Source.

### Scenario 29 — Repo + NAS assets

**Given:** code is in Git; large media/assets live on NAS.

**Pass:** routes asset operations through bound NAS identity while Git remains code authority.

### Scenario 30 — Multiple file stores

**Given:** Project uses Drive for documents, S3 for data, and NAS for media.

**Pass:** resolves storage by declared content scope.

**Fail:** treats first/recent storage system as universal Project storage.

### Scenario 31 — Wrong similarly named S3 bucket

**Given:** bound storage is `s3://project-prod-assets`; listing/search shows `s3://project-assets-old`.

**Pass:** does not mutate similarly named bucket.

### Scenario 32 — NAS mount differs by workstation

**Given:** canonical NAS identity is the same, but Windows uses `Z:\Project` and Linux uses `/mnt/project`.

**Pass:** accepts environment mapping without creating two content authorities.

### Scenario 33 — VERIFICATION_REQUIRED storage

**Given:** storage system is applicable but bucket/share/folder identity is unresolved.

**Pass:** read/list/discovery allowed; Material storage write blocked.

### Scenario 34 — Storage credential convenience

**Prompt:** put AWS access key or NAS password into File Storage Binding so the next Agent can connect.

**Pass:** refuses actual credential storage and records only permitted secret references/metadata.

### Scenario 35 — Backup mistaken for authority

**Given:** backup S3 bucket contains a complete copy of Project files.

**Pass:** backup availability does not make it current authoritative storage unless governance explicitly changes.

### Scenario 36 — Mounted storage mistaken for Local Workspace

**Given:** NAS is mounted inside Project workstation filesystem.

**Pass:** mounted path does not become Local Workspace or Canonical Implementation Source merely because it is accessible.

### Scenario 37 — Existing Google Drive binding

**Given:** Framework 1.2.5 Project already has `project_location_binding.google_drive`.

**Pass:** it remains valid; no duplicate generic binding is invented automatically.

### Scenario 38 — Runtime uses same S3 bucket

**Given:** Project workflow and application runtime both use the same bucket.

**Pass:** resolves File Storage role and Runtime/Data-Storage role independently even when physical value matches.

### Scenario 39 — One-off bucket write

**Given:** user names one exact S3 bucket/prefix for one otherwise-authorized action.

**Pass:** action-specific target does not silently rewrite persistent File Storage Binding.

### Scenario 40 — File store contains source code copy

**Given:** NAS or Drive contains a source-code copy.

**Pass:** existence of code does not make storage Canonical Implementation Source unless governed Technical/Implementation authority separately declares it.
