# Framework 1.2.5 Agent Continuity, Progressive Verification, and Local Workspace Binding Design

Status: DRAFT_FOR_USER_REVIEW

Scope approval: USER_EXPLICIT_APPROVAL — Candidates 1, 2, and 3 approved for the next Framework upgrade

Target Framework: `1.2.5`

Target Schema: `1.0.0` unchanged

Date: 2026-08-22

## 1. Goal

Release Project Source Framework `1.2.5` as a backward-compatible governance/workflow improvement that makes GPT-Web, Codex, MCP-backed agents, and other execution contexts continue work from the same durable state with less redundant verification and safer local workspace routing.

Framework `1.2.5` combines three approved improvements:

1. **Verified Material Task Completion Commit** — a Material Git-backed Task cannot become durably `DONE` while its required completed result exists only as uncommitted working-tree state.
2. **Progressive / Risk-Scoped Verification and Evidence Reuse** — Task verification is proportional to affected scope, dependency impact, and risk; full regression is reserved for semantic acceptance boundaries, and valid state-bound evidence may be reused.
3. **Environment-Scoped Local Workspace Binding** — Material local/MCP execution must resolve the Project's declared local workspace for the applicable execution environment rather than acting on whichever path/tool workspace is active or recently discovered.

## 2. Compatibility and Scope Boundary

Framework `1.2.5` MUST preserve:

- Project Source Schema `1.0.0`;
- semantic slots and Stable-ID families;
- `ACT DONE ≠ MS REACHED ≠ OUT ACHIEVED`;
- Framework `1.2.1` Externalized Working Memory / Logical Checkpoint / Chat Lifecycle semantics;
- Framework `1.2.2` Canonical Integration Target, Base Freshness, `STACKED_WORK`, and Pre-Merge Base Freshness Gate;
- Framework `1.2.3` Canonical Implementation Source / Development Workspace / Runtime Authority semantics;
- Framework `1.2.4` Project Location Binding, fail-closed connector routing, Chat Closure Consistency, and Mandatory Response Close;
- existing authority/risk rules and Project-local Framework pinning;
- no auto-upgrade for initialized Projects.

The upgrade adds no application code, validator product, hook, bot, CI/CD workflow, scheduler, background agent, filesystem watcher, automatic workspace selector, merge queue, or runtime enforcement service.

## 3. Approaches Considered

### 3.1 Task completion durability

**Rejected:** `Every Task MUST create exactly one commit.`

This would create noisy history, force commits for read-only Tasks, and encourage commits for failed/incomplete work.

**Selected:** A Material Task that changes an authoritative Git-backed repository requires a verified durable completion commit before it may be treated as durably `DONE`. Read-only/no-repository-mutation Tasks do not require a commit. One Task may use multiple coherent commits.

### 3.2 Verification depth

**Rejected:** full Framework/distribution verification after every Task or every Logical Checkpoint.

This repeats expensive checks even when only a small scope changed and conflates persistence checkpoints with release acceptance.

**Selected:** affected-scope/risk-proportional verification at Task level, continuity-focused verification at Logical Checkpoints, one full regression at Release Candidate/equivalent acceptance, and state-bound evidence reuse until invalidated.

### 3.3 MCP/local path identity

**Rejected:** canonical concept named `MCP Path` or binding directly to an MCP `workspaceId`.

MCP is an execution mechanism, not durable Project identity. Tool-specific workspace IDs may change across servers, installations, or environments.

**Selected:** **Environment-Scoped Local Workspace Binding** under Project Location Binding. The durable Project concept is the local workspace path/identity for an execution environment; MCP IDs are only runtime routing evidence.

## 4. Architecture

Framework `1.2.5` introduces no new authoritative document. The three improvements compose through existing homes:

```text
00 / FRAMEWORK-001
  → Project Location Binding, including Local Workspace Binding

15 Action Registry / Task execution semantics
  → completion verification + observed completion commit when applicable

09 Handoff
  → continuation pointers to Local Workspace Binding, repository/worktree/HEAD state,
    last completed Task/commit, verification state, and Exact Next Action when material

13 Evidence Registry
  → material reusable verification evidence when formal evidence is warranted;
    not every Task-local check requires a new EVD record

40 Technical Design
  → Development Workspace Contract / Canonical Implementation Source;
    references Local Workspace Binding when useful but does not duplicate its routing authority
```

Operational composition:

```text
WHERE may this agent/tool work?
→ Local Workspace Binding

WHAT source is authoritative Implementation Truth?
→ Canonical Implementation Source / Development Workspace Contract

WHAT must be verified for this change?
→ affected scope + dependencies + R0/R1/R2/R3 risk

WHEN may the Task become durably DONE?
→ required verification PASS + completed result represented by verified Git commit when applicable

HOW may another Agent continue?
→ durable commit/state + handoff pointers + valid verification evidence + Exact Next Action
```

## 5. Improvement A — Verified Material Task Completion Commit

### 5.1 Normative intent

For a Git-backed Task that materially mutates the Canonical Implementation Source or another authoritative repository artifact, `Task DONE` / `ACT DONE` requires a **Verified Task Completion Checkpoint**.

A Verified Task Completion Checkpoint means:

1. the Task's required scope is complete;
2. applicable affected-scope/risk verification has passed;
3. the required completed result is represented in one or more observed Git commits;
4. no required completed result for that Task exists only as uncommitted state;
5. the completion commit identity is observed rather than fabricated;
6. any remaining working-tree changes are understood and are not silently part of the completed Task.

The term is a workflow concept, not a new Project lifecycle state, Git freshness state, or Stable-ID family.

### 5.2 Exceptions and boundaries

- Read-only discovery/review/analysis with no repository mutation requires no commit merely to finish the Task.
- Failed, blocked, cancelled, or incomplete work cannot use a completion commit to claim successful `DONE`.
- WIP commits are allowed; `WIP commit ≠ Task DONE`.
- One Task may contain multiple atomic commits.
- `commit ≠ push`. Push/remote publication remains a separate shared-state/authority action.
- Cross-environment handoff is continuation-safe only if the receiver can access the completion commit through the same durable repository or a governed remote/shared transfer.
- Completion of an Action does not prove a Milestone or Outcome.

### 5.3 Handoff observability

When material to continuation, Handoff/Action state should be able to identify observed values for:

```text
Repository identity
Local Workspace Binding reference
Current work branch/worktree
Verified HEAD SHA
Working-tree state
Last completed Task / ACT
Completion commit(s)
Verification result/evidence pointer
Remote reachability/push state when needed for the receiving environment
Exact Next Action
```

These observations grant no branch or repository authority by themselves.

## 6. Improvement B — Progressive / Risk-Scoped Verification

### 6.1 Principle

Verification cost and depth MUST follow **affected scope + dependency impact + risk**, not the number of Tasks or a blanket rule to rerun every check.

Conceptual verification levels may be used in plans as operational labels:

```text
TASK_LOCAL_FAST
CHECKPOINT_INTEGRITY
RELEASE_FULL
INTEGRATION_GATE
```

These labels are planning/workflow vocabulary, not Project lifecycle states, epistemic states, or Stable-ID families. Core Governance should define the behavior rather than require Projects to persist the labels everywhere.

### 6.2 TASK_LOCAL_FAST

Before a Material Task becomes `DONE`, run the minimum sufficient checks that prove the affected behavior/invariants at the Task's risk level.

Examples:

- launcher-only change → launcher semantics, byte parity, size limit, affected regression cases;
- starter-stamp change → affected starter set/version consistency;
- normative rule change → affected semantic surfaces and direct pressure scenarios;
- read-only task → no execution test unless needed to support the conclusion.

Task-local verification MUST NOT automatically invoke unrelated full-distribution checks.

### 6.3 CHECKPOINT_INTEGRITY

A Logical Checkpoint primarily proves continuation safety:

```text
usable result persisted
completed Task commits identifiable
working-tree state understood
current blockers/pending state known
Exact Next Action durable
Required Read locations durable
affected cross-surface relationships valid when material
```

Logical Checkpoint does not mean `RELEASE_FULL` by default.

### 6.4 RELEASE_FULL

A completed Framework Release Candidate or equivalent semantic acceptance point receives full current-distribution verification once against the final candidate state. For ProjectFramework this includes all applicable current release identity, launcher parity/size, maintained starter, semantic invariant, pressure-scenario, and integrity checks required by the candidate.

### 6.5 Verification evidence reuse

Reusable verification evidence MUST be bound strongly enough to know what it proves. When material, capture/resolve:

```text
candidate/source identity or Git tree/HEAD
verification scope/profile or affected invariants
result
captured_at
relevant dependency state
relevant Canonical Integration Target state when the evidence depends on it
formal EVD reference only when evidence importance/risk requires registration
```

Prior evidence MAY be reused while its assumptions remain materially unchanged.

Evidence is invalidated selectively by events such as:

- candidate/source/tree changed in affected scope;
- relevant dependency materially changed;
- integration target moved in a way that changes applicable semantics/assumptions;
- verification rule/acceptance criterion changed;
- new evidence contradicts the verified state;
- validity cannot be bounded safely.

Uncertainty escalates verification; it does not justify assuming old evidence is valid.

### 6.6 Integration behavior

Immediately before integration, `INTEGRATION_GATE`:

1. re-resolves current Canonical Integration Target;
2. applies Framework `1.2.2` Base Freshness classification;
3. checks whether prior Task/Release verification evidence remains valid;
4. reruns only invalidated/newly affected checks unless impact cannot be bounded safely.

If integration is an exact fast-forward to the already verified candidate tree, post-merge normally confirms resulting target HEAD/tree, remote/shared state when applicable, and clean/understood workspace state rather than rerunning the full suite.

If rebase, conflict resolution, merge-time edits, semantic target movement, or another operation changes the previously verified resulting tree, affected/full verification escalates as required.

`Mergeable ≠ Acceptable` remains binding.

## 7. Improvement C — Environment-Scoped Local Workspace Binding

### 7.1 Purpose

Project Location Binding currently answers where GitHub and Drive work belongs. Framework `1.2.5` extends the same routing concept to Material local execution so an Agent cannot mutate the wrong Project merely because an MCP/editor/shell has another workspace active.

The canonical term is **Local Workspace Binding**, not `MCP Path`.

### 7.2 Canonical home and state vocabulary

Active local `FRAMEWORK-001` remains the canonical home. Local workspace routing reuses exactly:

```text
BOUND
NOT_APPLICABLE
VERIFICATION_REQUIRED
```

No new MCP-specific binding state is introduced.

`03 Current State`, `09 Handoff`, `40 Technical Design`, implementation plans, launchers, or MCP configuration may reference the binding but cannot maintain a second authoritative copy.

### 7.3 Environment scope

An absolute local path is environment-specific. Framework MUST NOT require the same physical path across every workstation, VM, WSL distribution, Dev Container, remote durable workspace, or other execution environment.

The root representation therefore supports one or more **environment-scoped local workspace entries**. A typical single-workstation Project may use one entry.

Each applicable entry resolves at least:

```text
Environment Scope / Key — Project-defined or user-confirmed context label
Binding State — BOUND | NOT_APPLICABLE | VERIFICATION_REQUIRED
Canonical Local Path — absolute path when BOUND
Repository Identity — owner/repository or canonical URL when Git-backed and material
Verification Status
Last Verified At
```

Exact template field names may be optimized during implementation, but these semantics are fixed.

If Material local work is requested in an execution environment for which no applicable verified entry can be resolved, the effective local binding is `VERIFICATION_REQUIRED` unless Root Governance explicitly makes local execution `NOT_APPLICABLE`.

### 7.4 BOUND minimum

For local workspace `BOUND` in the applicable environment:

- the canonical local Project/workspace path is verified or user-confirmed;
- the actual tool/MCP execution path matches when comparison is possible;
- for Git-backed work, repository identity/origin is cross-checked when practical so a same-named folder/clone does not silently satisfy routing;
- tool-specific IDs may corroborate the observation but are not canonical identity.

### 7.5 Fail-closed behavior

`VERIFICATION_REQUIRED` permits read-only/list/search/inspect operations needed to resolve the workspace but blocks Material local mutation by default.

`NOT_APPLICABLE` blocks Material local/MCP Project work for that declared scope/environment until a governed Root Governance binding/scope change.

A User Explicit Instruction naming one exact local target may authorize that single otherwise-permitted action under the existing Framework `1.2.4` one-off-target rule. It does not persistently rewrite Local Workspace Binding.

Persistent binding change requires User Explicit Approval plus `FRAMEWORK-001` revision → validate → promote → supersede/archive flow.

### 7.6 Tool identity and MCP

MCP `workspaceId`, editor workspace handle, recent-workspace list, active window/folder, search ranking, and similar tool/runtime metadata are **observed routing evidence only**. They MUST NOT become canonical Project identity or silently transfer routing authority.

This allows the same Project rule to govern:

```text
GPT-Web → Tai-F3_MCP
Codex → local shell/worktree
Claude → another MCP/local tool
Human → IDE/terminal
```

without changing Project identity merely because the executor changes.

### 7.7 Required semantic separation

```text
Repository Location Binding
≠ Local Workspace Binding
≠ current branch/worktree
≠ Canonical Integration Target
≠ Canonical Implementation Source
≠ Runtime Location
```

Local Workspace Binding answers **where the local execution surface may operate**.

Canonical Implementation Source / Development Workspace Contract answers **which durable source determines IMPLEMENTATION Truth**.

Current branch/worktree and Canonical Integration Target remain Git integration concerns.

Runtime Location remains RUNTIME Truth/execution topology.

These values often align in a simple local Git Project, but alignment does not collapse their meanings.

## 8. GREENFIELD and Migration

### 8.1 GREENFIELD

Before active `FRAMEWORK-001` exists:

```text
canonical Framework bootstrap reads
→ read-only discovery of GitHub / Drive / local workspace candidates as needed
→ Preview proposed Project Location Binding, including applicable local environment entries
→ explicit user approval
→ create active 00 / FRAMEWORK-001
→ subsequent Material connector/local work resolves active binding
```

Unknown local path is not guessed from active editor folder, MCP ranking, recent workspaces, repository name similarity, or chat memory.

### 8.2 Existing initialized Projects

Existing Projects remain pinned to their current Framework until a governed `MIG-*` upgrade.

Migration to `1.2.5` MUST NOT invent:

- local filesystem paths;
- environment scope identity;
- completion commit provenance;
- verification evidence;
- repository origins;
- MCP workspace identifiers.

For Local Workspace Binding:

```text
verified/user-confirmed environment + path → BOUND
local execution applicable but unresolved → VERIFICATION_REQUIRED
local execution outside declared Project scope → NOT_APPLICABLE
```

## 10. Pressure / Acceptance Scenarios

Framework `1.2.5` should add pressure scenarios covering at minimum:

1. Material Task edits complete but required files remain uncommitted → cannot claim durable `DONE`.
2. Read-only Task completes → no synthetic commit required.
3. WIP commit exists but verification fails → WIP commit does not imply `DONE`.
4. Completion commit exists locally but receiving Agent is remote and cannot access it → handoff not continuation-safe until governed transfer/publication.
5. Small launcher-only change → affected launcher verification only at Task level; no unrelated full starter scan.
6. Logical Checkpoint after several verified commits → continuity checks without unconditional full release regression.
7. Release Candidate full verification PASS bound to candidate HEAD.
8. Pre-Merge target unchanged + candidate unchanged → reuse full verification evidence.
9. Integration target moves non-semantically without invalidating assumptions → rerun only required freshness/affected checks.
10. Candidate tree changes after full verification → affected evidence invalidated.
11. Exact fast-forward of verified candidate → minimal resulting-state confirmation.
12. Merge conflict resolution changes tree → affected/full re-verification required.
13. MCP active workspace is another Project → Local Workspace Binding blocks Material mutation.
14. Same folder name but wrong Git origin → repository cross-check blocks Material mutation.
15. MCP `workspaceId` changes but verified canonical path/repository remain correct → no persistent binding rewrite required.
16. Project used from two machines with different paths → environment-scoped entries allow both without one global path.
17. Unknown new execution environment → `VERIFICATION_REQUIRED` until resolved.
18. Local execution `NOT_APPLICABLE` → accessible MCP does not grant Material local scope.
19. One-off exact local target instruction → action-specific only; persistent binding unchanged.
20. Local workspace path equals Canonical Implementation Source in simple Git Project → meanings remain distinct even when values align.

## 11. Verification Strategy for the 1.2.5 Implementation Itself

The implementation plan SHOULD exercise the improvement being introduced without pretending it is already authoritative for old Projects:

```text
Each Material implementation Task
→ affected-scope/risk verification
→ completion commit

Logical checkpoint/handoff
→ continuity integrity only + affected cross-surface checks

Final 1.2.5 candidate
→ one RELEASE_FULL-equivalent verification

Immediately before merge
→ Framework 1.2.2 Base Freshness + evidence validity check

After exact fast-forward
→ resulting-state confirmation
```

If implementation changes after full verification, invalidate and rerun only affected evidence unless impact cannot be bounded safely.

## 12. Success Criteria

Framework `1.2.5` is design-complete only if the resulting current distribution makes all of these unambiguous:

- an Agent can determine which local workspace it may mutate before Material local/MCP work;
- local workspace routing cannot silently redefine repository/branch/integration/implementation/runtime authority;
- a Material Git-backed Task cannot be durably `DONE` with required completed state only uncommitted;
- read-only or no-repository-mutation Tasks are not forced to create meaningless commits;
- Task verification is proportional to scope/dependency/risk rather than blindly full;
- Logical Checkpoint does not imply full release regression;
- full verification evidence can be reused when its bound state/assumptions remain valid;
- invalidation/escalation is fail-closed when uncertainty is material;
- existing 1.2.1–1.2.4 governance remains intact unless explicitly amended;
- Schema stays `1.0.0` and no new Stable-ID/state family is created;
- launchers remain within size/parity constraints;
- existing initialized Projects do not auto-upgrade.
