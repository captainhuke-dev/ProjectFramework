# Framework 1.3 Command Contract and Direct-to-Latest Upgrade Design

Status: USER_APPROVED_DIRECTION / IMPLEMENTATION_AUTHORIZED

Date: 2026-08-23

## Goal

Release Project Source Framework `1.3.0` / Schema `1.0.0` with two related usability improvements:

1. a small, discoverable bracketed Project command contract for fresh Project status/path inspection; and
2. a direct-to-latest cumulative upgrade architecture whose cost scales with the current-to-target semantic delta rather than the number of skipped releases.

The release also hardens mandatory response-close rendering so bracketed fields such as `[Chat]:` remain visibly renderable in Markdown without changing canonical lifecycle tokens.

## Scope Boundary

Framework 1.3 remains conceptual governance/documentation first. It defines command and migration semantics; it does **not** introduce a command parser service, CLI, bot, watcher, scheduler, migration engine, CI/CD workflow, or automatic updater.

Existing initialized Projects remain locally pinned and never auto-upgrade. Upstream 1.3 becomes authoritative only for NEW Project bootstrap or after an initialized Project completes an explicitly approved governed migration.

## Architecture

### 1. Registered Bracketed Project Commands

The Framework maintains a small semantic command registry. A registered command name is recognized only when enclosed by literal `[` and `]`; matching of the registered name inside the brackets is case-insensitive. Whitespace/casing normalization may identify a registered command, but missing brackets do not.

Initial registry:

```text
[Project Status] : fresh-read Project identity, Task state, Git sync/working-tree state, verification, blockers, and health
[Project Path]   : show/verify configured bootstrap path values and accept an explicit request to change them through existing location governance
```

Natural-language requests such as “มีชุดคำสั่งอะไรบ้าง”, “available commands”, or “command list” invoke command discovery behavior, not a new mandatory bracketed command. Discovery lists only currently registered commands as `[XXX] : purpose`; it must not invent unsupported commands.

### 2. `[Project Status]` Contract

`[Project Status]` is read-only. It must fresh-observe available Project/runtime sources instead of answering from chat memory.

Presentation order:

```text
Identity
→ Health
→ Remain Tasks
→ Git Sync
→ Working Tree
→ Verification
→ Blockers
```

Minimum semantics when applicable:

- **Identity:** Project/repository, Workspace, current branch/ref, observed HEAD.
- **Health:** use existing Framework health vocabulary `GREEN | AMBER | RED | UNKNOWN`; do not invent a competing `YELLOW` state.
- **Remain Tasks:** count incomplete Task records and show Task ID, state, and concise detail when the task source exposes detail.
- **Git Sync:** remote/tracking target, ahead/behind counts, divergence, and remote freshness. Claim `VERIFIED` only after a fresh remote observation/fetch for the report; otherwise use `STALE` or `VERIFICATION_REQUIRED` as diagnostic report labels, not new Framework lifecycle states.
- **Working Tree:** `Waiting Commit: Yes/No`, changed-file count, staged, unstaged, and untracked counts.
- **Verification:** latest applicable result `PASS | FAIL | NOT_RUN | UNKNOWN` and evidence-validity context when available.
- **Blockers:** material blockers or `None` when verified absent.

Task count and Git change count are distinct. Git cannot infer how many logical Tasks are represented by changed files; therefore “Waiting Commit” is Yes/No plus change/file counts, not an invented Task count.

If a required source/tool cannot be observed, report `UNKNOWN` / `VERIFICATION_REQUIRED` for that dimension rather than fabricate current state.

### 3. `[Project Path]` Contract

`[Project Path]` shows the configured Project Settings/bootstrap values:

```text
Framework Remote Path: <FRAMEWORK_REMOTE>
Git Remote Path: <GIT_REMOTE>
Storage Path: <STORAGE>
MCP Path: <MCP_PATH>
Workspace Path: <WS>
```

Any value still syntactically represented by an angle-bracket placeholder such as `<STORAGE>` or `<WS>` means **unset / not configured**. It is not a literal path and must not be replaced by an inferred recent/active/mounted/similarly named location.

The command may also carry an explicit user request to change one or more path values. Reading/verification remains read-only. A persistent change still uses existing Bootstrap/Project Location governance: one-off exact targets are action-specific; persistent governed binding/location changes require explicit approval and the applicable `FRAMEWORK-001` revision/validation/promotion/history flow.

### 4. Markdown-Safe Mandatory Response Close

Observed regressions show that a governed response may visibly omit `[Chat]`. Bare Markdown text beginning a paragraph with `[Chat]: value` can be interpreted by some Markdown renderers as reference-definition syntax. Framework 1.3 therefore separates **semantic label** from **presentation wrapper**.

Canonical semantic labels remain exactly:

```text
[Next Action]:
[Chat]:
[Reason]:
[Required Read]:
```

Recommended Markdown-safe rendering is:

```text
**[Next Action]:** <value>

**[Chat]:** CONTINUE_CURRENT_CHAT | START_NEW_CHAT

**[Reason]:** <value>

**[Required Read]:** <value>
```

The wrapper is presentation-only. The completeness gate validates one visible semantic field of each kind, in order, lifecycle-consistent, with Required Read final. Canonical lifecycle tokens remain unescaped.

### 5. Framework 1.3 Direct-to-Latest Upgrade Architecture

The core invariant is:

> Upgrade cost should scale with the affected semantic difference between the current reconstructable Project state and the approved target Framework, not with the number of releases skipped.

An initialized Project migration does **not** execute each historical Framework amendment/migration sequentially merely because those releases existed. Historical amendments, Git history, and prior `MIG-*` records remain provenance/rationale and are never deleted.

Direct-to-latest flow:

```text
resolve active current Project / local pin
→ materialize current reconstructable truth
→ resolve explicitly selected target Framework distribution
→ compare current state directly with target required semantics
→ classify affected target semantics
→ choose migration path
→ Preview cumulative delta + preservation/rollback plan
→ explicit approval
→ apply only required current→target changes
→ affected/risk-scoped verification
→ RELEASE_FULL once on final unchanged target candidate
→ promote target Framework revision and preserve superseded/history state
```

Target-delta assessment categories may use these planning/report labels:

```text
ALREADY_SATISFIED
REQUIRED
NOT_APPLICABLE
VERIFICATION_REQUIRED
CONFLICT_REVIEW
```

They are assessment labels, not new Project lifecycle/Epistemic/authority state families.

### 6. Migration Path Classes

Framework 1.3 defines exactly three direct-upgrade path classes:

- **`FAST_PATH`** — current reconstructable state is compatible with the target and the required target delta is bounded with no material unresolved conflict. Apply only the necessary delta after normal migration approval.
- **`ASSESSED_PATH`** — semantic changes require a cumulative `MIG-*` assessment/plan, but direct current→target migration remains safe without replaying each intermediate release.
- **`MAJOR_MIGRATION_REQUIRED`** — direct migration cannot be safely bounded because of breaking schema/namespace/root-governance changes, non-reconstructable current truth, or material unresolved conflicts/unknowns. Use a separately approved major migration/reconstruction plan.

Skipping intermediate **execution** never means skipping compatibility assessment, authority, approval, rollback, validation, preservation, or evidence.

### 7. Rebuild Boundary

The maintained starter represents the current target shape for NEW Projects. It is not a license to delete/recreate an initialized Project Source during normal upgrade.

A full rebuild/reconstruction from the latest starter is not the default upgrade path because it can lose Project-specific rules, Stable IDs, current decisions/requirements, bindings, authority, migration/history, and provenance. Reconstruction is allowed only when classified `MAJOR_MIGRATION_REQUIRED` and explicitly approved with preservation/mapping rules.

### 8. Verification and Evidence Reuse

Framework 1.3 reuses Framework 1.2.5 progressive verification:

- migration tasks run minimum sufficient affected/risk verification;
- logical checkpoints use `CHECKPOINT_INTEGRITY`, not blanket full regression;
- final unchanged target candidate receives one `RELEASE_FULL`;
- `INTEGRATION_GATE` rechecks Base Freshness/evidence validity and reruns only invalidated scope unless impact cannot be safely bounded.

The Framework does not execute `RELEASE_FULL` once per skipped historical release.

## Distribution Changes

Framework 1.3.0 updates current distribution surfaces only:

- release descriptor and README;
- new latest amendment;
- Core Governance and `SKILL.md`;
- root/starter/migration/bootstrap templates;
- maintained mockup README;
- compact ChatGPT/Claude launchers;
- pressure scenarios.

Historical amendments remain unchanged.

`FRAMEWORK-RELEASE.yaml` gains declarative `upgrade_policy` metadata. `release_format_version` advances to `3` because the descriptor shape gains a governed top-level upgrade-policy block; Schema remains `1.0.0` because no Project Source semantic slot or Stable-ID namespace changes.

## Safety and Compatibility

- No auto-upgrade.
- No silent persistent path rewrite.
- No invented placeholder/path values.
- No loss of current Stable IDs/history/project-specific rules.
- No new branch authority or Project Location `canonical_branch`.
- No executable updater/parser/validator runtime.
- `commit ≠ push` remains unchanged.
- Existing initialized Projects continue under their pinned Framework until migration is explicitly approved and promoted.

## Acceptance Criteria

1. Pressure scenarios cover all command, response-close, and direct-upgrade failure modes before normative implementation.
2. All current Framework surfaces declare 1.3.0 / Schema 1.0.0 consistently; historical files are untouched.
3. Launchers remain <= 4,500 Unicode characters and marker bodies are byte-identical.
4. Mandatory close has a Markdown-safe visible rendering form while semantic field/token vocabulary remains unchanged.
5. Direct-to-latest semantics preserve governance/history while eliminating mandatory intermediate migration execution.
6. One final `RELEASE_FULL` passes on the unchanged candidate and is bound to observed candidate state.
