# CONST-020 — Frameworks, extensions, and adopted mechanisms

Frameworks and extensions operate under Project Law and this Constitution.

They do not become constitutional authority merely because they are installed, popular, bundled, referenced, or remembered.

Project Law determines which frameworks and extensions are adopted, their scope, immutable identity, allowed effects, and conflict handling.

A framework or extension MUST NOT weaken constitutional requirements.

## Communication extension

The Constitution defines Communication Integrity but does not require a specific writing tool.

A project MAY adopt a communication extension to fill this slot.

Project Law names the extension and MUST pin it to an immutable, verifiable identity appropriate to its source system. A version label is not an identity: two artifacts can carry the same version label and differ in content, and this has been observed in practice for a communication extension used in this project line. Pin the immutable identity, not the label and not a mutable branch.

The extension remains subordinate to Communication Integrity and Decision Integrity.

The extension MUST NOT transform constitutional law, Project Law, machine packets, schemas, identifiers, evidence records, or quoted source material in place.


## Context substrates

A Project MAY adopt a context substrate such as a memory database, retrieval system, vector store, semantic cache, or agent context database.

The substrate remains an adopted mechanism under Project Law. It has no constitutional authority by installation, indexing, retrieval rank, or memory persistence.

Project Law MUST define its allowed scope, identity/pinning, namespace/isolation boundary, write effects, secret-handling boundary, outage/degradation behavior, and relationship to canonical Project truth when material governed work depends on it.
